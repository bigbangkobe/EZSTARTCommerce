## 3. 已知风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 真实渠道未接 | 无法线上收款 | 先上 COD；渠道到位后新增适配器（5–10 人日），业务代码不动 |
| 烟草类目收单受限 | 渠道可能直接拒批 | 支付方式可随时停用；前台按连接状态自动隐藏，不会出现"下单必失败" |
| 同机多实例端口未参数化 | 第二客户不能与首个客户共机 | 一客户一实例（本就在设计内）；共机需求留到 W9 |
| 前端应用目录按商户名硬编码（`storefront-<id>`） | 新客户需手工建目录 | 复制流程已写入交付清单，W9 改为生成 |
| identity 双实例竞态用例在高并发跑全量时偶发 ECONNRESET | 本地回归噪音 | 单文件运行 22/22 通过；属本机资源争用，非代码缺陷。CI 建议 `--test-concurrency=2` |
| 对账任务依赖主机 cron | 漏配则退化为无对账 | 交付清单强制项；未配时端点 503 而非静默 |

## 4. 发布与回滚

### 4.1 上线当日顺序

1. **备份**：`pg_dump` 全量 + 记录当前镜像标签与 commit。
2. **迁移**：`docker compose run --rm migrate`（Prisma 只前进，不回滚）。
3. **发布**：`docker compose up -d --build api admin storefront`。
4. **健康检查**：`/api/v1/health/ready` 200，且迁移清单与库内记录逐条一致。
5. **冒烟**：首页 200、商品页 200、加购 → 下单（COD）→ 后台看到订单。
6. **支付冒烟**（渠道就绪后）：后台填凭证 → 测试连接 `ok` → 下测试单 → 支付 → 退款。
7. **对账**：手动跑一次 `scripts/reconcile.mjs`，确认返回计数且无 `errors`。
8. **签字**：10 项逐条勾选，记 `configHash`。

### 4.2 回滚

```bash
cd /opt/ezstart-mrinhk/deploy/merchants/mrinhk
docker compose down
docker tag ezstart-mrinhk-api:previous ezstart-mrinhk-api   # 或从 registry 拉旧标签
docker compose up -d
```

迁移不回滚。回滚代码前必须确认新迁移对旧代码是**向后兼容**的（本次
`202611200400_refund_event_types` 只放宽 CHECK 约束，向后兼容）。

### 4.3 本次新增迁移的兼容性

| 迁移 | 内容 | 向后兼容 |
|---|---|---|
| `202611200400_refund_event_types` | `RefundEvent.type` CHECK 增加 `dispatched / provider_pending / refunded` | ✅ 只放宽，旧代码不受影响 |

### 5.1 备份恢复与升级演练（实测）

在生产库上执行，全程只读 + 恢复到 staging 独立库，不影响生产：

| 步骤 | 命令 | 结果 |
|---|---|---|
| 备份 | `pg_dump -Fc`（容器内） | 318 KB，**<1 秒** |
| 恢复到独立库 | `pg_restore -d restore_drill` | **2 秒**，无报错 |
| 结构比对 | 表数 / 订单 / 商品 / 管理员 / 迁移数 | 95 / 2 / 1 / 1 / 35 —— 与生产完全一致 |
| **升级演练** | 在对生产数据副本上跑 `migrate deploy` | 新增 `202611200400_refund_event_types` 应用成功，迁移数 35 → **36** |
| 约束校验 | `pg_get_constraintdef` | `RefundEvent_type_check` 已包含 `refunded / dispatched / provider_pending` |

这一步的价值：**证明新迁移能直接跑在现有生产数据上**，不需要清库、不需要人工补数据。
这是发布前唯一无法靠测试用例替代的验证。

## 6. 烟草客户复制清单（A 类配置交付）

按设计，第二个客户不需要改业务代码。交付时要做的：

| 步骤 | 动作 | 产出 |
|---|---|---|
| 1 | 填写 `instance.yaml`（品牌、主题、市场、合规、部署） | `configHash` |
| 2 | `pnpm instance:validate` | 校验通过 |
| 3 | `pnpm instance:bundle` | 标准部署包 |
| 4 | 复制 `apps/storefront-<id>` 并改主题 token | 前台应用（当前需手工） |
| 5 | `pnpm instance:init` | 目录、`.env`、密钥就地生成 |
| 6 | 起实例 → 迁移 → 健康检查 | 可访问 |
| 7 | 后台配支付（含测试连接） | 收银台可用 |
| 8 | 10 项签字 + 冒烟 | 交付确认 |

**已知需要手工的两步**：第 4 步的前台目录、第 6 步的端口（同机场景）。这两项已列入 W9。
