# EZSTARTCommerce 架构基线

完整的产品与技术设计见 [产品与技术总体蓝图](../01-产品文档/PRODUCT_TECHNICAL_BLUEPRINT.md)；本文保留架构摘要。

## 1. 架构目标

- 同一套核心可为不同商家配置和独立部署。
- 商品与交易流程通用，行业/市场差异通过配置、策略和适配器扩展。
- 本项目保持可理解、可调试和易交接，不为多租户 SaaS 预先拆分微服务。
- 管理后台、客户专属顾客前台、业务 API、数据库、文件存储和第三方服务职责清楚。

## 2. 推荐架构

首期采用**模块化单体**，以一个主要业务 API 和一个主数据库承载交易；前台和后台可以位于同一应用仓库的不同应用/路由。同一代码版本可为多个商家重复部署，但每家使用独立运行环境、数据库、媒体空间和凭证。通知、导入等耗时任务通过 PostgreSQL outbox/job 表及独立 Worker 处理。

| 层次 | 建议职责 |
|---|---|
| 顾客前台 | 客户专属的响应式店面；通过稳定 API 使用商品、访客结账和自愿会员 OTP 能力 |
| 商家后台 | 登录/权限、商品/订单/促销/库存/内容、SEO/URL、隐私请求和报表管理 |
| 应用服务/API | 商品目录、交易、订单、支付/配送策略和后台操作用例 |
| 数据层 | PostgreSQL 主数据、事务及迁移 |
| 媒体层 | 对象存储保存商品图片和导入文件 |
| 异步任务 | PostgreSQL outbox/job 表驱动邮件/短信/WhatsApp/OTP 发送、积分入账/过期、批量导入、报表导出；至少一次投递并幂等消费 |
| 外部服务适配器 | 支付、通知、物流等可替换连接器 |
| 运维层 | 日志、告警、备份、密钥管理、发布与回滚 |

## 3. 技术栈（已冻结）

采用 TypeScript + Node.js 24 LTS；前台/后台使用 Next.js 16 + React；API/Worker 使用 NestJS 12 模块化单体；数据库使用 PostgreSQL 18；持久化使用 Prisma ORM 7 GA，涉及锁与精确交易时使用显式数据库事务/参数化 SQL；API 使用 REST JSON + OpenAPI；异步任务使用 PostgreSQL outbox/job 表，首期不依赖 Redis；媒体使用 S3 兼容对象存储；应用以 Docker 镜像和 Docker Compose 独立部署。pnpm workspace 与 lockfile 固定精确依赖版本。

架构细节、API/错误契约、交易金额、状态机、权限、部署门槛和升级规则统一见 [开发执行规格](DEVELOPMENT_SPEC.md)。精确 patch 版本由仓库 lockfile 锁定，安全/兼容更新走依赖变更评审。

## 4. 模块边界

- Identity & Admin：管理员、角色、权限、审计。
- Store Configuration：品牌、语言、市场、功能开关。
- Catalog：商品、规格、分类、品牌、搜索。
- Content/Merchandising：页面、FAQ、公告、文章、翻译、主题区块配置和商品陈列优先级；多语言 SEO、索引、Sitemap 与重定向。
- Commerce：购物车、结账、订单和状态机。
- Payments & Reconciliation：付款方式、服务商适配器、支付/退款台账和服务商结算文件对账。
- Fulfillment：配送区域、运费和履约记录。
- Customer/Membership：顾客档案、会员等级/积分流水、OTP 登录会话、营销同意、权益计算和个人资料请求工作流。
- Promotions：优惠券、规则和核销。
- Inventory：库存数量、预留和变动账目。
- Communications：通知模板、任务和发送状态。
- Analytics/Import：经营报表、网站事件漏斗和批量数据工作流。
- AfterSales：售后案件、退款协调、退货质检和库存处置，依赖订单/支付/库存域接口，不直接修改原始交易记录。

各域之间通过应用接口调用；模块之间不得直接绕过业务规则修改对方数据。

## 5. 外部集成原则

- 支付服务商必须由业主选择并取得业务批准；按适配器封装创建支付、回调验签、查询和退款能力。
- 通知服务支持邮件基础能力，其他渠道独立配置；不得把营销通知和交易通知混在一起。
- 物流首期采用后台人工履约；之后按承运商 API 单独接入。
- 授权管理员可在后台录入服务商凭证；后端立即写入密钥管理服务，业务数据库只保存引用，后台不回显明文。初始部署凭证也可由部署密钥注入；密钥不得进代码仓库、普通配置表或日志。
- 服务异常需记录、重试或进入人工处理队列。

## 6. 部署与模板升级

- 每个商家首期有独立环境、数据库、文件空间、后台账号、域名和第三方凭证；不同商家之间不共享订单、顾客、库存、报表或媒体文件。
- 代码版本与商店配置、商家数据分开。
- 数据库变更通过版本化迁移文件交付。
- 升级流程：备份 → 测试环境验证 → 发布 → 健康检查 → 必要时回滚。
- 客户专属页面和交互在独立前端包/项目实现，并通过稳定版本化 API 连接其电商核心。
- 客户前端可独立视觉设计和发布；商家通用内容由对应后台配置。
- 通用商品、价格、库存、优惠和订单规则留在核心服务端，前台只展示和调用，不自行决定交易金额。
- 共享核心升级前，对客户独立前端执行 API 兼容检查和回归验收。
- 模板方不默认集中采集商家的业务或分析数据；代运维访问需授权并审计。

## 7. 多客户交付规模化

本项目通过重复部署同一版本化核心来交付新客户，不建设共享商家控制平面、跨店运营后台或集中业务数据分析。客户数量增加时，优化的是实例开通、升级、备份和支持流程；每个客户的数据与运行环境仍保持独立。
