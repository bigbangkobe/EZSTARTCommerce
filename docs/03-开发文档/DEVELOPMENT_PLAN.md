# mrinhk 上线开发方案与排期

> 版本：v1.0　日期：2026-11-20　状态：**已定档（方案 C：7 周 / 35 工作日）**
> 范围：现有 mrinhk 实例直接上线；AWS Lightsail 东京；COD + 线上支付（可配置通道）；S3、监控、ECR、压测、完整交接。
> 依据：[技术架构 v2.0](ARCHITECTURE.md) · [支付适配器规格](PAYMENT_ADAPTER_SPEC.md) · [开发执行规格](DEVELOPMENT_SPEC.md) · [M08 支付](../01-产品文档/modules/M08_PAYMENTS.md) · [实例配置规范](../01-产品文档/INSTANCE_CONFIG_SPEC.md)
> 后续：mrinhk 上线后按同一流程复制烟草客户实例（W8 为复制前置）。

---

## 0. 结论先行

1. **已定档方案 C：7 周 / 35 工作日**。理由：mrinhk 上线后要立刻复制烟草客户，只有做完 S3、监控、ECR、压测、运维交接，第二个实例才是"复制"而不是"重做"。
2. **支付不靠"后台配置"凭空产生**：`providers` 白名单目前只有 `cod` / `manual_bank_transfer`，线上通道的适配器、回调入口、密钥解析三段代码都不存在。本期先做**可插拔适配器 + 后台可配账号**，详见 [支付适配器规格](PAYMENT_ADAPTER_SPEC.md)。
3. **一次性投入换可复制性**：适配器抽象做对之后，第二个客户接自己收单账号只需后台配置 + 连接测试，不改代码。
4. **两个外部阻塞依然存在**：烟草合规书面意见、收单类目批复与沙箱凭证。开发可并行，但上线日期不可承诺。

## 1. 当前基线

### 1.1 已具备

| 能力 | 现状 |
|---|---|
| 应用 | `api` / `admin` / `storefront-mrinhk` / `worker` 四应用可构建运行 |
| 交易底座 | 商品、购物车、订单、支付台账、库存预占、售后、退款、对账基础 |
| 配置化前台 | `ThemeConfig` + 区块注册表 + 发布快照 + 前台渲染 |
| 实例交付 | `instance.yaml` 校验、实例目录生成、初始化 CLI、批量升级 CLI |
| AWS 运行 | Lightsail 东京 `ap-northeast-1`，2 vCPU / 4 GB / 100 GB，Amazon Linux 2023 |
| 入口 | Caddy 80/443，自动 HTTPS；DB/API/Worker 不暴露公网 |
| CI | GitHub Actions：契约校验、类型检查、测试、后台构建、浏览器测试 |
| 测试基线 | 纯单元 231/231 通过；领域相关 27/27 通过；HTTP 集成需数据库环境 |

### 1.2 上线缺口

| 缺口 | 影响 | 优先级 |
|---|---|---|
| 线上支付适配器缺失 | 目前只有 `cod` 与 `manual_bank_transfer`，无法在线收款 | **P0 阻塞** |
| 年龄核验/健康警示未产品化 | 烟草商城合规不能上线 | **P0 阻塞** |
| S3 媒体未启用 | 媒体与主机耦合，扩容/迁移困难 | P0 |
| CloudWatch/告警未接 | 故障发现依赖人工 | P0 |
| 备份恢复未演练 | 无法证明 RTO/RPO | P0 |
| staging 环境未隔离 | 无法安全做支付/迁移演练 | P0 |
| 服务器构建镜像有 OOM 风险 | 4 GB 构建 Next.js 可能失败 | P1 |
| CI 未构建/推送镜像 | 发布依赖服务器本地构建 | P1 |
| 本地 Node 22 / 项目 Node 24 不一致 | 本地命令与 CI 行为不一致 | P1 |
| 新实例无 storefront 应用 | `APP_DIR: apps/storefront-<id>` 无对应目录，第二客户起实例会失败 | P1（复制前必修） |
| migrate 未自动构建镜像 | 手工分步执行 `up migrate` 会拉不到镜像 | P1（复制前必修） |
| compose 模板硬编码旧服务器信息 | 新客户实例带出 mrinhk 服务器信息 | P1（复制前必修） |
| Caddy 端口硬编码 80/443 | 同机多实例演练端口冲突 | P1（复制前必修） |

## 2. 上线范围

### 2.1 Must（不上线不可）

- COD 下单、收款、拒收、退回、对账闭环。
- **支付通道可插拔**：适配器接口、Registry、SecretResolver（AWS Secrets Manager）、统一回调入口 `POST /webhooks/payments/:provider`。
- **一个**线上支付通道跑通：创建支付、回调验签、幂等、查询、退款、失败/未知处理、连接测试。
- **后台可配**：客户在 Admin 填商户号/环境/密钥引用/显示名，点连接测试 → verified → 启用，全程不改代码、不重启。
- 烟草合规：年龄门、结账强校验、健康警示、牌照信息留存、销售限制（按法务意见）。
- mrinhk 主题/品牌/首页区块由配置驱动，前后台发布链路可用。
- AWS staging 部署 + 生产部署 + 域名 HTTPS + 健康检查。
- 备份/恢复演练一次，记录 RTO/RPO。
- 10 项上线阻断签字完成。
- 核心测试用例通过：交易、支付、库存、权限、部署冒烟。

### 2.2 Should（强烈建议本期）

- S3 媒体存储 + 最小权限 IAM + 私有 Bucket。
- CloudWatch 日志/指标/告警 + 外部 uptime。
- GitHub Actions 构建镜像推 ECR，服务器只拉取。
- 性能冒烟：首页、商品页、结账、支付回调。
- 安全复核：公网端口、密钥、RBAC、审计、TLS。

### 2.3 Could（可下一期）

- 运维代理、批量升级可视化、自动回滚。
- 第二个线上支付通道。
- 多语言内容/SEO 深度优化。
- 会员营销自动化。

### 2.4 Won't（本期不做）

- 共享多租户 SaaS、跨店数据中台。
- 微服务拆分、Kubernetes。
- B/C 类深度定制页面（除合规必需）。
- 自建支付网关或存储卡数据。

## 3. 工作分解与工作量估算

> 人日为工程估算，不含客户审批、支付开户、法务意见等待时间；实际以排期评审为准。

| 编号 | 工作流 | 交付物 | 估算人日 | 依赖 |
|---|---|---|---:|---|
| W1 | 合规与上线门禁 | 合规清单、年龄门、健康警示、牌照留存、10 项签字表 | 5–8 | 客户/法务意见 |
| W2 | 支付适配器抽象 | 接口契约、Registry、SecretResolver、统一回调入口、后台配置校验 | 6–8 | 无（可先做） |
| W3 | 线上支付通道 | 一个渠道适配器、创建/查询/退款、验签、沙箱联调、连接测试 | 8–12 | W2、收单沙箱 |
| W4 | COD 与对账 | COD 待收/已收/拒收/退回、结算导入、差异队列、线上拉单补状态、死信 | 4–6 | W3、财务口径 |
| W5 | AWS 加固 | staging 隔离、S3 媒体、CloudWatch 告警、备份恢复演练、ECR 镜像发布 | 10–14 | AWS 权限 |
| W6 | 前台与配置 | 主题发布链路、年龄门 UI、健康警示位、内容配置、支付方式前台展示规则 | 6–8 | W1、主题引擎 |
| W7 | 测试与验收 | 测试用例、集成/回归、安全复核、性能压测 | 9–12 | W2–W6 |
| W8 | 上线与交接 | 上线 Runbook、UAT、生产发布、hypercare、运维交接 | 5–7 | W7 |
| W9 | 第二客户复制准备 | 前台应用生成、migrate 预检、模板去硬编码、Caddy 端口参数化 | 3–5 | W8 |

**合计约 56–80 人日**（含测试与交接）。按 4 人并行（后端 1、前端 1、测试 1、运维 1）＋产品/合规 0.5，工程周期约 **7 周（35 工作日）**；外部审批与沙箱等待另计。

W9 与 W8 的后半段并行，不额外拉长关键路径。

### 3.1 优先级说明

本期用 MoSCoW 控制上线范围，不套 RICE：RICE 需要客户覆盖与业务影响数据，当前只有单客户上线目标， Reach 均为 1，排序会失真。上线后再用 RICE 排 B/C 类需求。

## 4. 排期方案对比

| 方案 | 周期 | 范围 | 人员假设 | 风险 | 适用 |
|---|---|---|---|---|---|
| A. 2 周冲刺 | 10 个工作日 | **仅 COD**；线上支付不上；合规最小集；S3/监控后补 | 后端 1 + 前端 1 + 测试 0.5 | 高：合规与支付一旦卡住即延期 | 只有硬性截止日、且客户接受 COD 先上线 |
| B. 4 周稳妥上线 | 20 个工作日 | COD + **一个**线上支付；合规门禁；AWS staging/prod；备份恢复；基础监控 | 后端 1 + 前端 1 + 测试 1 + 运维 0.5 | 中：取决于支付沙箱与合规意见 | **推荐** |
| C. 6–8 周完整体 | 30–40 个工作日 | B + S3 + CloudWatch + ECR + 性能压测 + 完整交接 | 后端 1 + 前端 1 + 测试 1 + 运维 1 | 低：范围完整，便于复制第二客户 | 无硬截止、追求可复制交付 |

**结论：选 C。** 本期目标不只是"mrinhk 能上线"，而是"上线后可复制"。B 方案把 S3、监控、ECR、压测推到上线后，会在第二个客户时以"重做"的形式补回来，总成本更高。

## 5. 方案 C 排期（7 周 / 35 工作日）

> 每周末设门禁，门禁不过不进下一阶段。

### 第 1 周：合规冻结、支付抽象、环境准备

- 合规清单确认：牌照、年龄核验方式、健康警示文案、广告限制、配送复核、数据留存。
- 收单机构确认：类目是否允许烟草、沙箱账号、回调域名、退款能力、结算文件格式。
- **支付适配器抽象**：`PaymentAdapter` 契约、Provider Registry、`SecretResolver`、`/webhooks/payments/:provider` 骨架、后台配置校验（白名单键、`secret://` 协议、`connectionStatus` 门控）。
- AWS staging 实例/域名/证书/安全组；生产实例只读核对。
- S3 Bucket + IAM 最小权限设计。

**门禁 G1**：合规清单签字版 + 支付抽象层合入主干（含单测） + staging 可访问。

### 第 2 周：线上支付通道 + 密钥管理

- 一个渠道适配器：创建支付、查询、退款、验签、错误码归一化。
- Secrets Manager 接入：引用解析、TTL 缓存、启动期校验（生产拒绝 `env`/`file` 形态）。
- 后台"测试连接"：verified / failed 状态回写，失败原因脱敏。
- 回调链路：rawBody 验签、`dedupeKey` 幂等、未知单进死信、验签失败 400。
- 沙箱联调：成功 / 失败 / 取消 / 退款 / 重复回调 / 乱序回调。

**门禁 G2**：沙箱完成 6 类支付场景；重复回调不重复入账；日志无密钥明文。

### 第 3 周：COD 对账 + 前台合规

- COD 待收/已收/拒收/退回、结算导入、差异队列。
- 线上渠道拉单补状态任务（`pending` 超 15 分钟）+ 死信重放。
- 年龄门：入口拦截 + 结账强校验 + 配送复核，不可通过刷新/改参绕过。
- 健康警示位：商品页、结算页按法务文案展示。
- 主题发布链路：后台配置 → 发布快照 → 前台渲染。
- 支付方式前台展示规则：`enabled && verified` 才可见。

**门禁 G3**：COD 与线上各跑通一笔全链路；年龄门绕过测试全部失败。

### 第 4 周：AWS 加固

- staging 与生产隔离（独立实例/独立 DB/独立域名）。
- S3 媒体：上传、读取、生命周期、私有 Bucket + 签名 URL。
- CloudWatch：日志组、指标、告警（5xx、支付失败率、回调积压、证书到期）。
- GitHub Actions 构建镜像推 ECR，服务器只拉取，消除 4 GB OOM 风险。
- 备份策略 + 恢复演练一次（记录 RTO/RPO）。

**门禁 G4**：S3 与监控可用；恢复演练达标；镜像发布链路通。

### 第 5 周：测试与安全复核

- 按 [上线验收测试用例](../04-测试文档/TEST_CASES_LAUNCH.md) 执行全量：交易、支付、库存、权限、主题、部署冒烟、烟草专项。
- HTTP 集成测试在 CI 独立 PG 跑通（`--test-concurrency=4`）。
- 安全复核：公网端口、密钥、RBAC、审计、TLS、CSP、越权测试。
- 性能压测：首页、商品页、结账、支付回调；给出容量结论。
- 缺陷修复，功能冻结。

**门禁 G5**：P0/P1 缺陷为 0；安全复核无高危；压测达标。

### 第 6 周：UAT 与上线

- 客户 UAT：真实商品、真实订单、真实退款、后台操作、支付配置自助流程。
- 10 项上线阻断签字。
- 生产发布：备份 → 迁移 → 发布 → 健康检查 → 冒烟。
- 回滚演练一次。
- Hypercare：上线后 3 天值守。

**门禁 G6**：10/10 签字 + 生产冒烟通过 + 回滚演练通过。

### 第 7 周：交接与复制准备

- 运维 Runbook：发布、回滚、备份恢复、密钥轮换、告警处置。
- 客户运营培训：商品、订单、支付配置、退款、对账。
- **第二客户复制准备**：新实例前台应用生成、migrate 预检、compose 模板去硬编码、Caddy 端口参数化（W9）。
- 复制演练：用烟草客户配置起一个 staging 实例，验证"只改配置不改代码"。

**门禁 G7**：复制演练成功 + 运维交接签字。

## 6. 关键路径与依赖

```text
合规意见 ─┐
          ├→ 年龄门/健康警示 ─┐
支付沙箱 ─┘                   ├→ 联调 → 测试 → UAT → 上线
AWS 权限 → staging/S3/监控 ───┘
```

| 依赖 | 类型 | 最晚就绪 | 不就绪的替代 |
|---|---|---|---|
| 烟草合规书面意见 | 阻塞 | 第 1 周末 | 不上线；只做技术预研 |
| 线上支付沙箱/凭证 | 阻塞 | 第 2 周初 | **抽象层照做**（不依赖沙箱），渠道适配器延后；COD 先行 |
| AWS SSH/Route 53/IAM 权限 | 阻塞 | 第 1 周初 | 无法部署，排期顺延 |
| 客户 UAT 人员 | 并行 | 第 6 周初 | 内部验收替代，风险上升 |
| S3 权限 | 并行 | 第 4 周初 | 暂用本地媒体，上线后迁移 |

> 支付抽象（W2）与沙箱无关，可先合入主干；这是把支付从关键路径上摘下来的关键动作。

## 8. 验收口径

- [ ] COD 与线上支付各完成至少 1 笔成功、1 笔失败、1 笔重复回调测试。
- [ ] 支付 `unknown` 不被误判失败，不释放库存/优惠占位。
- [ ] 未登记渠道无法被后台启用；`secret://` 引用可解析；日志检索不到密钥明文。
- [ ] 后台完成"填配置 → 测试连接 → 启用"后，**不重启服务**即在前台生效。
- [ ] `enabled=true` 但连接未 verified 时，前台不展示该支付方式。
- [ ] 年龄门不可通过简单刷新/改参数绕过；结账与配送环节均有校验。
- [ ] 商品页/结算页健康警示按法务文案展示。
- [ ] 10/10 上线阻断签字完成。
- [ ] 备份恢复演练完成，RTO/RPO 有记录。
- [ ] 公网仅 80/443；数据库/API/Worker 无公网端口。
- [ ] 监控告警可触发并送达责任人。
- [ ] 发布与回滚各演练一次。
- [ ] 测试用例全部通过，无 P0/P1 缺陷。
