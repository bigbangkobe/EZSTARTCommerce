# EZSTARTCommerce 项目实施方案

> 当前版已采用 [开发执行规格](DEVELOPMENT_SPEC.md) 中冻结的产品/工程基线。下文历史工作量仅留作旧规划记录，不能据此给完整核心或客户前台承诺价格/工期；新版估算须按当前模块范围、团队配置和首店客户参数重新核算。

## 1. 项目目标

交付可复用、可独立部署的通用电商核心与管理后台，并完成一套参考前台。每位客户的独立定制前台按其页面与交互范围另行设计、开发和验收。核心包含三语、访客结账、商品/订单管理、会员运营、优惠券、配送/付款配置、库存预警、经营报表、网站访问分析、批量导入和私有部署交接。

本方案以产品和技术需求已获业主确认、外部服务商账户由业主提供为前提。支付账户审批、域名迁移、法规审核和第三方消息服务审批不属于开发方可控的工期。

## 2. 交付方法

建议按两周一个迭代的敏捷方式推进，每个阶段均产生可演示成果。需求变更进入变更清单，评估对价格、工期、数据和验收的影响后再纳入。

### 阶段 A：发现与范围冻结（1–2 周）

- 按默认基线在客户云账号内部署；确认云区域、备份目标、支持时段。若客户选择代托管则单独签 SLA/报价。
- 确定首发市场、商品范围、合规审核责任人。
- 冻结访客结账与自愿会员 OTP 边界、会员积分/等级规则、语言、币种、支付、配送和通知服务商；具体客户参数走上线参数表。
- 产出产品需求基线、模块验收条件、数据字段和优先级。

### 阶段 B：体验与系统设计（1–2 周）

- 绘制通用顾客/商家关键流程，并为首个目标客户梳理专属前台旅程。
- 制作后台、会员中心、首页/分类/搜索/商品/购物车/结账、付款/订单异常状态原型；客户专属页面另行评审。
- 定义多语言内容模型、权限矩阵、订单状态机及服务接口。
- 产出通用核心视觉规范、客户前台原型、架构图、稳定 API/数据模型初稿和迭代计划。

### 阶段 C：平台基础与管理框架（2–3 周）

- 建立代码仓库、环境、持续集成、数据库、后台登录、角色权限、操作日志和配置管理。
- 建立商店配置、语言/地区/货币/时区框架。
- 建立可重复部署、实例初始化、域名/HTTPS 配置和实例隔离基础。
- 建立主题、内容和模块开关基础。

### 阶段 D：商品、内容与前台（3–4 周）

- 实现商品/分类/品牌/规格/图片管理和批量导入。
- 实现三语内容编辑、首页/页面/FAQ/文章。
- 在商品浏览、加购和结账路径布置匿名分析事件。
- 实现一套通用参考前台、商品搜索、分类浏览和商品详情，供模板演示和通用基线使用；每位客户的前台按批准的页面与交互方案独立开发，并连接该客户自己的后台 API。
- 完成商家配置后的店铺预览。

### 阶段 E：交易与履约（3–4 周）

- 实现购物车、优惠券校验、访客结账和订单建立。
- 实现订单后台、状态流转和顾客订单通知。
- 实现配送规则配置和货到付款。
- 实现基础售后案件：取消、退款记录、退货/换货进度和库存处置；服务商退款能力单独确认。
- 接入一个获批线上支付方式，并完成测试环境/生产凭证配置流程。

### 阶段 F：运营功能（2–3 周）

- 实现后台顾客/会员档案、等级/积分/权益规则、OTP 登录与会员中心、优惠券、库存预警、经营报表和网站转化漏斗。
- 实现通知服务配置及失败记录。
- 完成导入导出、数据校验和错误报告。

### 阶段 G：集成、验收和上线（2–3 周）

- 业务验收、跨语言检查、响应式检查、权限检查、备份恢复演练和生产发布。
- 修正验收问题，交付操作手册、部署手册、管理员培训和版本说明。
- 上线后短期问题处理期，时长和响应级别写入合同。

## 3. 初步工作量与日历工期

**估算边界：**历史建议基线 181–277 人日仅供参考，未完整计入当前的 OTP 会员中心/积分规则、结算文件对账、分批发货与库存超时恢复、MFA/会话管理、前台陈列配置及端到端生产就绪验收，不能用于完整范围固定报价。需要在模块接口、客户服务商、经营规则和验收范围冻结后重新估算核心工作量。该估算亦不含任何客户的专属视觉设计、独立页面/交互开发、客户差异接口联调或内容迁移。烟草站作为一个客户前台案例，需按单独确认的页面和流程范围另行估算，除非合同明确将其列为额外交付工作包。

| 工作包 | 估算（人日） |
|---|---:|
| 需求发现、产品管理和范围冻结 | 10–15 |
| UX/UI 与可用性原型 | 12–18 |
| 平台基础、后台认证、权限和配置 | 14–20 |
| 店铺设置、多语言、地区配置 | 8–12 |
| 基础参考前台、主题、内容管理 | 15–22 |
| 商品目录、导入导出 | 15–23 |
| 购物车、结账、订单 | 18–26 |
| 付款与配送 | 13–22 |
| 会员/顾客、优惠券、库存 | 待按完整会员范围重估 |
| 通知与报表 | 16–26 |
| 集成、验收、质量与安全检查 | 18–28 |
| 私有部署、文档、培训和交接 | 9–14 |
| 跨模块集成和估算余量 | 4–6 |
| M16 售后、取消、退款案件 | 10–16 |
| **历史基线合计（会员扩展前，非报价）** | **181–277 人日** |

旧规划曾按 2 名全栈开发、0.5 名产品/项目经理、0.5 名设计师及部分 QA/DevOps 投入估出 **17–26 周（会员扩展前历史估算）**。这不是当前排期；完整核心需对 M00–M16 重估，每位客户的专属前台另计。支付服务商审批、商品资料质量、市场审查或新增集成会影响实际日历工期。

## 4. 里程碑与交付物

| 里程碑 | 完成标准 |
|---|---|
| M1 范围冻结 | 客户上线参数表关键项、会员/交易规则、部署责任和客户前台范围获签字 |
| M2 原型确认 | 关键顾客/后台页面流程已评审，三语策略明确 |
| M3 基础后台可演示 | 后台登录、权限、店铺配置、商品录入可演示 |
| M4 商品与前台可演示 | 商品导入、分类搜索、参考前台可用；首个客户专属前台完成独立验收范围确认 |
| M5 端到端下单可演示 | 访客可从选购到订单建立，后台能处理订单 |
| M6 付款/配送/运营完成 | 获批支付、配送规则、优惠券、库存预警、经营报表及网站转化分析可验收 |
| M6.1 售后闭环 | 售后案件、退款状态、退货质检和库存处置满足确认后的范围 |
| M7 上线交付 | 两套独立实例部署验证通过；客户定制前台按独立范围验收；备份恢复、升级回滚、培训、文档和账号交接完成 |

## 5. 建议人员与责任

- **产品负责人/业主：**业务规则、市场范围、内容与翻译、法规和支付商户审核、最终验收。
- **项目/产品经理：**需求管理、优先级、里程碑、风险和变更控制。
- **UX/UI 设计：**流程、响应式页面、组件规范及原型。
- **开发团队：**前台、后台、数据、接口和部署实现。
- **QA：**按验收标准进行功能、权限、浏览器、语言和回归验收。
- **DevOps/安全：**环境、密钥、备份、监控、发布和恢复流程。

## 6. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 首店会员积分/等级具体值及 OTP/通知服务账户尚未提交 | 影响首店配置、短信费用及服务商联调 | 邮箱 OTP、安全规则和积分数据模型已冻结；客户参数表补会员规则，短信服务商选定后估算差异 |
| 烟草销售法规或支付服务商不允许某些业务 | 功能无法上线或账户被冻结 | 上线市场、商品、支付和营销先由业主及专业顾问审核 |
| 线上支付账户审批慢 | 交易阶段延期 | 开发前申请商户账户；先做 COD 和支付适配层，服务商批准后接入 |
| 没有旧站后台和数据 | 初始目录录入工作量增加 | 业主整理 CSV/图片；导入功能按标准模板验收 |
| 三语内容缺失或翻译不一致 | 页面不完整、结账误解 | 明确每种语言责任人和缺译降级策略 |
| 客户前台定制与核心代码混杂 | 升级成本、缺陷增加 | 独立前端包/项目，依赖稳定 API；客户定制与通用核心分别版本化 |
| 支付、短信、WhatsApp 接口变动 | 运营中断 | 采用适配器、监控失败和可切换配置 |
| 顾客资料/订单资料处理不当 | 隐私与安全风险 | 数据最小化、权限、加密、日志遮蔽和保留策略经目标市场审核 |
| 需求不断加项 | 工期和预算失控 | 维护范围基线和变更单，按优先级进入后续迭代 |

## 7. 验收与变更管理

- 每个模块以其模块规格中的验收条件为准。
- 端到端流程至少覆盖商品维护、三语展示、访客下单、会员 OTP/积分、优惠、配送费、付款异常状态、后台处理、通知和报表。
- 上线前完成管理员角色检查、数据备份和恢复演练、第三方凭证确认及商家培训。
- 新增市场、第二支付服务、密码式或强制顾客账号、多仓、物流 API 或原数据迁移均需书面评估变更；基线内的自愿 OTP 会员不作为变更项。

## 8. 上线后的运营

- 定义模板版本号、发行说明、升级兼容性和回滚方式。
- 约定安全更新、备份频率、监控负责人及事故联系人。
- 汇总商家反馈，按季度规划模板版本。
- 付费插件、主机、短信、邮件、WhatsApp 和支付交易费用由合同单独列明。
