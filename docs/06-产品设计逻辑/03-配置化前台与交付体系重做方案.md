# 配置化前台与交付体系重做方案

> 状态：产品重做基线（待评审）
> 日期：2026-11-20
> 定位：本文是「前台定制方式 + 交付体系」这一层的重做方案，不是全盘推倒。交易底座（资金、状态机、库存、权限、合规）原样继承。
> 关联：[设计逻辑总览](00-设计逻辑总览.md) · [定制模型现状](../01-产品文档/CUSTOMIZATION_MODEL.md) · [M02 前台](../01-产品文档/modules/M02_STOREFRONT.md)

## 0. 决策摘要（一页读懂）

| 项 | 内容 |
|---|---|
| **要解决的问题** | 现有设计默认「每客户独立设计开发前台」，是项目制，无法规模化；与「底座复用 + 轻配置 + 独立部署」的真实定位冲突 |
| **重做范围** | 只重做「前台定制方式 + 实例配置 + 交付工具链」这一层；交易底座完整保留 |
| **核心决策** | 前台从**硬编码**改为**配置驱动**；A 类配置级定制成为**默认路径**，B/C 类工程级降为例外增值 |
| **不做的改变** | 不做 SaaS、不做多租户共享、不改资金/状态机/库存/权限规则、不改独立部署边界 |
| **目标形态** | 换客户 = 填一份实例配置 → 一键拉起独立实例 → 客户得到专属电商系统，全程不需要前端开发 |
| **商业意义** | 从「做项目」转为「卖产品」：边际成本趋近于零，可规模化复制 |

## 1. 现状诊断（基于代码事实，非文档推测）

### 1.1 一句话结论

项目目前是**单实例、单店铺、主题硬编码在前端源码里**。文档写的 "配置化前台" 与代码现实存在**三层脱节**。

### 1.2 三层脱节

| 层 | 文档怎么说 | 代码实际 | 后果 |
|---|---|---|---|
| **数据层** | M02 列出 `ThemeConfig`/`HomepageSection`/`NavigationItem`/`StorefrontPreference` | Prisma 里**一个都不存在**；只有 `StoreConfig`、`MerchandisingLayout` | 主题无任何持久化载体 |
| **表现层** | "主题/组件注册表声明可配置区块" | 品牌名、配色、字体、WhatsApp、hero/about 结构、市场码全部硬编码在 `site.ts`/`i18n.ts`/`page.tsx`/`globals.css` | 换客户必须改代码+重新构建 |
| **交付层** | "独立部署 +  commissions 升级" | 8 步人工部署，`CLIENT_LAUNCH_INPUTS` 是人工核对表；无标准部署包、无一键起实例 | 每多一客户 = 多一轮人工，边际成本不降 |

### 1.3 可复用的现成骨架（好消息）

改造不必从零造轮子，已有一套成熟模式：

- **`MerchandisingLayout` 的发布模型**：草稿（`sections` JSON）→ 发布快照（`publishedSnapshot`）→ 版本号（`version`）→ 未发布返回 404 → 前台降级到默认布局。这套"配置安全发布"机制可直接复用到主题配置。
- **`StoreConfig` 已有品牌字段**：`logoMediaId`、`faviconMediaId` 已在数据库，只是前端没读、后台没上传 UI。
- **`/api/v1/storefront/config` 已被前台消费**：`lib/analytics-client.ts` 已在读它的 `features`，扩展返回 theme 字段成本很低。
- **`MERCHANDISING_SECTION_TYPES = ['product_grid']`**：这是组件注册表的雏形，可扩展为声明式注册表。

## 2. 新定位与产品边界

### 2.1 重新定义产品

> **EZSTARTCommerce = 一套可配置、可独立部署的电商底座。交付一个客户 = 一份实例配置 + 一次标准部署，而非一次前端开发项目。**

### 2.2 不变的边界（红线）

- ❌ 不做共享多租户 SaaS、不做商户总控台、不做跨店数据汇总
- ❌ 不改资金底线：服务端算价、状态分离、幂等对账、库存预占、退款限额
- ❌ 不改独立部署：一商家一实例一数据库一域名，数据不出客户服务器
- ❌ 不把任何行业（烟草）规则写死进核心

### 2.3 改变的边界（本次重做）

- ✅ 前台定制从"独立开发"改为"配置驱动"（默认）
- ✅ 首页布局从"硬编码区块"改为"区块注册表 + 后台编排"
- ✅ 客户上线输入从"人工核对表"改为"机器可读的实例配置源"
- ✅ 部署从"人工 8 步"改为"标准包 + 一键起实例"

## 3. 新的 A/B/C 定制模型

### 3.1 模型定义（A 类成为默认）

| 类型 | 名称 | 客户能改什么 | 是否需要前端开发 | 交付方式 | 定位 |
|---|---|---|---|---|---|
| **A** | 配置级（默认） | 品牌色、Logo、字体、首页区块与顺序、模块开关、文案、语言、商品陈列、政策页 | ❌ 不需要 | 填配置 → 部署 → 上线 | **产品化路径，主推** |
| **B** | 视觉级（例外） | A 类 + 全新设计系统、定制组件样式、独特动效 | ✅ 需要（有限） | 配置 + 主题包开发 | 增值服务，单独报价 |
| **C** | 工程级（例外） | B 类 + 全新页面结构、专属选购流程、外部系统深度集成 | ✅ 需要（完整） | 独立前端工程 | 少数大客户，单独报价 |

### 3.2 关键转变

- 旧模型：烟草按 **C 类**评估 → 暗示"每个客户都要定制开发"
- 新模型：**A 类是默认交付**，只有客户明确需要独特流程/设计时才走 B/C，并单独计费
- 商业含义：把"稍微改布局"从特例变成默认路径，客户才会觉得"买的是产品而非项目"

### 3.3 判定流程

```
客户提出定制需求
    ↓
能否用 A 类的配置项表达？（品牌/区块/开关/文案）
    ├─ 能 → A 类，配置交付，标准报价
    └─ 不能 → 是否需要新视觉设计？
                  ├─ 只要新样式 → B 类，主题包开发，单独报价
                  └─ 要新页面/流程 → C 类，独立前端，单独报价
```

## 4. 目标架构（四根支柱）

```
┌─────────────────────────────────────────────────────────────┐
│                      实例配置源 (Instance Manifest)            │
│   一份机器可读配置，驱动：部署参数 + 前台主题 + 业务规则         │
└───────────────┬─────────────────────────────┬───────────────┘
                │                             │
                ▼                             ▼
┌───────────────────────────┐   ┌──────────────────────────────┐
│   支柱①  前台配置引擎        │   │   支柱③  交付工具链             │
│  ThemeConfig + 区块注册表   │   │  标准部署包 / 一键起实例 /       │
│  + 发布快照 + 前台渲染        │   │  批量升级 / 轻量运维代理        │
└───────────────┬───────────┘   └──────────────────────────────┘
                │
                ▼
┌───────────────────────────┐
│   支柱②  后台配置台         │   ← 支柱④ 商业分层贯穿全程
│  品牌/主题/布局/陈列 可视化配置 │
└───────────────────────────┘
```

### 支柱① 前台配置引擎

- **ThemeConfig 模型**（单行，仿 `MerchandisingLayout` 的发布模式）：
  - 品牌：`brand`、`brandLatin`、`tagline`、`logoMediaId`、`faviconMediaId`
  - 视觉：`primaryColor`、`inkColor`、`paperColor`、`fontPair`、`radius`
  - 联系：`whatsappNumber`、`whatsappGreeting`
  - 结构：`navigation`（JSON）、`homeSections`（JSON，区块类型 + 参数 + 顺序）
  - 发布：`draftConfig`、`publishedSnapshot`、`version`、`publishedAt`
- **区块注册表**：在 `packages/domain` 定义声明式注册表，每个区块声明 `{type, 字段 schema, 默认参数}`。首期区块：`hero`、`about`、`product_grid`、`rich_text`、`faq`、`content_card`。
- **前台渲染**：新增 `lib/theme.ts`（照搬 `lib/merchandising.ts` 的 envelope + revalidate + 404 降级），`page.tsx` 由 `homeSections` 驱动渲染，`layout.tsx` 注入 CSS 变量与品牌外壳。

### 支柱② 后台配置台

- 新增 `theme` 配置页：品牌、配色、字体、导航、首页区块编排（可视化增删改排序）。
- 表单由**区块注册表的 schema 驱动**，新增区块类型时后台表单自动适配，不改后台代码。
- 沿用 `merchandising-console` 的"草稿 → 发布 → 撤下"三段式与审计。
- 补齐 `settings-console` 里已有 DB 字段但无 UI 的 `brandAssets`（logo/favicon 上传）。

### 支柱③ 交付工具链

- **标准部署包**：版本化 Docker 镜像（api/admin/worker/storefront）+ compose 模板 + migration runner。
- **一键起实例**：读入实例配置 → 校验 → 生成 `.env` → 初始化数据库（StoreConfig/MarketProfile/ThemeConfig）→ 拉起全家桶 → 冒烟测试。
- **批量升级**：版本清单 + 兼容性检查 + 每实例独立升级脚本（先备份、再验证、可回滚）。**不需要 SaaS 中控**——工具链是本地/CLI 或客户侧执行，不集中任何客户数据。
- **轻量运维代理（可选）**：装在客户实例内，做监控/备份/日志回传，客户数据不出内网。

### 支柱④ 商业分层

- A 类：标准产品交付，固定价，目标是 X 天上线（具体天数由团队确认）。
- B/C 类：单独报价，作为增值服务，不纳入标准产品承诺。
- 报价结构：底座授权 + 实例部署 + A 类配置（标准）｜ B/C 类开发（另计）｜ 持续维护升级（年费）。

## 5. 实例配置源（Instance Manifest）设计

### 5.1 目标

把 `CLIENT_LAUNCH_INPUTS`（115 行人工核对表）升级为**机器可读的单一配置源**：一次填写，同时驱动部署、前台主题、业务规则，消除重复录入与人为遗漏。

### 5.2 配置分组（草案）

```yaml
instance:
  id: client-hk-001
  domain: shop.example.com
  market: HK
  currency: HKD
  locales: [zh-HK, zh-CN, en]
  defaultLocale: zh-HK
brand:                          # → ThemeConfig
  name: IN先生
  brandLatin: Mr. IN
  tagline: 心を込めて、凡事認真。
  logo: /media/logo.png
  primaryColor: "#BC002D"
  fontPair: editorial-jp
  whatsapp: "85260474794"
storefront:                     # → 首页区块编排
  homeSections:
    - type: hero
      params: { ... }
    - type: product_grid
      params: { sectionId: featured, title: 精选, limit: 6 }
    - type: about
      params: { ... }
business:                       # → 业务规则（沿用现有 StoreConfig）
  payment: [cod, approved_gateway]
  shipping: { regions: [...], freeThreshold: 500 }
compliance:                     # → 上线阻断项
  privacyPolicyUrl: ...
  ageGateRequired: false
deploy:                         # → 交付工具链
  cloud: { provider: ..., region: ... }
  backup: { frequency: daily, retention: 30d }
```

### 5.3 校验与阻断

- 配置有 schema 校验，缺必填项不能进入部署。
- 交易相关未确认项（支付账户、税费口径、隐私责任人）标记为**上线阻断**，签字前不允许生产发布。
- 配置版本化，每次变更可追溯、可回滚。

## 7. 风险与应对

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| 配置化能力不足，客户仍需改代码 | 中 | 高 | 严格按 A 类判定流程；配置覆盖不了的走 B/C 单独报价，不硬塞 |

| 文档与代码再次脱节 | 中 | 高 | 每份文档标注"代码现状"与"目标态"，本方案作为唯一基线 |
| 商业模型不清晰导致报价混乱 | 中 | 中 | A/B/C 分级 + 标准报价表，配置级默认、工程级另计 |
