# 模块设计逻辑（M00–M16）

> 本文展开 [设计逻辑总览](00-设计逻辑总览.md) 第 3.2、4 节：对 17 个业务模块逐一讲清 **"为什么需要它 → 负责什么 → 关键设计逻辑与意图 → 与谁协作"**。
> 这是逻辑梳理而非规则抄录；完整范围/数据对象/验收标准以 `01-产品文档/modules/M00–M16` 原文为准，横切规则以 `03-开发文档/DEVELOPMENT_SPEC.md` 为准。

## 模块地图与依赖脉络

```
平台层     M15 部署隔离 ──▶ M00 后台权限 ──▶ M01 店铺设置/市场规则
                                    │
商品内容层  M03 商品 ◀── M05 导入    M04 内容/陈列 ──▶ M02 前台/SEO
              │                │            │
交易层      M06 结账 ──▶ M07 订单 ──▶ M08 支付/对账
              │            │  └──▶ M09 配送
              └──▶ M12 库存 ◀───────┘
运营层      M10 会员  M11 优惠  M13 通知  M14 报表
售后层      M16 售后（关联订单/支付/库存）
```

阅读提示：多数模块都复用总览第 4 节的横切模式（服务端裁定、预占—核销—释放、幂等、状态机、快照、权限分级）。下文只强调**该模块特有的设计逻辑**。

## 平台与身份

### M00 管理后台、账号与权限
- **为什么需要**：多人协作的后台必须有"谁能看什么、能做什么"的可控边界，否则数据泄露与误操作不可追责。
- **设计逻辑**
  - 权限码下沉到服务端，每个 API/导出/异步下载都要登记权限码——UI 隐藏不是安全边界。
  - 顾客账号与后台员工账号彻底分离；员工唯一账号、禁共用凭证。
  - 高权限角色强制 MFA（TOTP + 恢复码）；会话可撤销，账号停用/权限收紧后旧会话立即失效。
  - 审计只增不改删，且不含密码/OTP/密钥/完整银行资料。
  - 隐私请求的"读取/核验/审批/处理/导出"拆成不同授权，避免一个角色拿到全部隐私数据权限。
- **协作**：依赖 M15 实例初始化；向所有后台模块提供 RBAC 与审计能力。

### M01 商店设置、多语言与市场规则
- **为什么需要**：同一模板服务不同商家/市场，品牌、语言、币种、时区、合规必须可配置而非写死。
- **设计逻辑**
  - 地区配置只是业务参数，**不替代法律判断**：未审核市场默认禁止下单，市场过期读取时即时收敛。
  - 年龄/资格验证策略可配，但流程须经目标市场审核；汇率与多店自动切换首期不做。
  - 配置变更留审计，前台按店铺设置展示。
- **协作**：影响商品、价格、结账、通知、报表；依赖后台基础与部署配置。

### M15 私有部署、实例开通、安全与模板升级
- **为什么需要**：这是"每商家独立实例"设计落地的基础设施，决定隔离、交接与升级是否可靠。
- **设计逻辑**
  - 一实例 = 一商家 = 一站点；多站点建多实例，避免一个后台误操作影响多站。
  - 代码版本与商家配置/数据分离——升级不覆盖商品、订单、主题配置；升级前备份 + 预发布验证 + 回滚步骤。
  - 交接/停服导出明确覆盖范围，但密钥/支付凭证/OTP/会话令牌不进通用导出；销毁不能宣称"即时从所有备份清除"，按备份周期轮转。
  - 默认不建集中运维控制台；代托管需临时授权访问并留记录。
- **协作**：可先于业务模块交付；与全部模块联合做安全/恢复/交接验收。

## 商品与内容

### M03 商品、分类、规格与搜索
- **为什么需要**：商品目录是电商的数据地基，SKU/价格/库存/翻译的规范程度决定下游交易能否可靠。
- **设计逻辑**
  - SKU 店内唯一、价格用最小货币单位；下架商品不可加购，规格库存与可售状态必须一致。
  - 发布门禁：每种启用语言的名称/详情/SKU 文案齐全才允许发布，**缺译阻断而非静默回退或机翻**。
  - 订单保存下单语言与商品翻译快照，后续改名改价不影响历史订单。
- **协作**：依赖 M00/M01 与媒体存储；被 M05/M02/M12 消费目录契约。

### M04 内容管理（含前台陈列）
- **为什么需要**：让商家不改代码即可维护内容页与首页/分类/专题陈列，同时守住发布与 SEO 的正确性。
- **设计逻辑**（本项目实现最深的模块之一）
  - 草稿与发布分离：草稿改动不影响公开地址；发布固化为不可变快照 `ContentPageVersion.snapshot`，前台只读快照。
  - 跨语言原子发布（同一事务切换），缺语言返回明确错误码；撤下清空 slug、回滚用历史快照建新版本。
  - 区块注册表白名单：只接受已注册区块与字段，拒绝 HTML/脚本/未知字段——不提供任意代码编辑，保证安全与可升级。
  - 手工排序与动态排序互斥（切换时自动清空，服务端再校验），避免"以为生效其实没生效"。
  - **陈列作用域按 id 绑定**（`home | category:<uuid> | collection:<uuid>`），分类/专题改名不改 slug 不丢版面；这与"用稳定 id 而非可变 slug 做关联"的整体原则一致。
  - 商品资格在**发布时与前台读取时双重校验**：下架/市场不可售商品立即隐藏，动态区块由后续合格商品补足。
  - SEO：slug 变更登记 301（含成环/遮挡检测并清理），预览 token 库里只存 SHA-256、短时有效、不加载埋点。
  - 发布计数器 `cr-N` 作为埋点版本，让陈列效果可按真实内容版本分组。
- **协作**：依赖 M00/M01/M02/M03；前台按发布契约渲染；worker 处理定时发布。

### M05 商品导入与导出
- **为什么需要**：批量录入是商家自助运营的关键效率点，但批量写入是最容易污染数据的地方。
- **设计逻辑**
  - 先预览后执行：明确新增/更新/跳过/错误行，重复 SKU、冲突匹配、未知字段不猜测处理。
  - 每行独立事务 + 支持"仅应用有效行"或"整批原子"两种策略；中断可幂等续跑；不默默删除未出现在文件中的商品。
  - 库存字段不得直接覆盖，必须生成带原因的库存调整流水（呼应 M12）。
  - 远程图片导入防 SSRF：仅 HTTPS、限制重定向/大小/超时、拒绝内网/本机/云元数据地址。
  - 导出权限与数据权限分离、临时文件过期、链接短时有效。
- **协作**：依赖 M00/M03/M12/M15。

### M02 前台主题与店铺体验
- **为什么需要**：给客户前台一个可运行的参考基线，并定义它如何安全接入核心。
- **设计逻辑**
  - 客户前台按批准的站点地图/视觉稿独立开发，不限换色换标；它依赖生成的 API 客户端，不复制规则、不连库。
  - 主题以注册表声明可配置区块；商家在后台编辑这些区块与商品顺序，发布后前台同步。
  - SEO 技术基线：canonical/alternate、sitemap、robots、slug 301；关键元数据须在初始 HTML 可被搜索引擎读取，不能只靠浏览器异步插入。
- **协作**：依赖设计系统、M01/M03、稳定 API 契约；CMS 内容由前台按发布契约读取。

## 交易与履约

### M06 购物车、优惠应用与访客结账
- **为什么需要**：它是"访客结账优先"这一核心决策的落地点，也是交易一致性的第一道关口。
- **设计逻辑**
  - 访客购物车随机会话标识持久化、30 天过期；结账前不保存非必要联系资料。
  - 服务端重算价格/折扣/运费/库存，浏览器金额不可信；报价变化需顾客二次确认。
  - 优惠券与限量会员权益下单时原子预占，订单终态再核销或释放；支付结果未知不释放。
  - 幂等键防重复建单；支付跳转/返回页不作到账依据，结果以服务端订单/支付状态为准。
  - 会员 OTP 是可选入口而非前置条件；无通知服务或 OTP 故障不阻断访客结账。
- **协作**：依赖 M01/M03/M07/M08/M09/M11/M12，是交易闭环的编排者。

### M07 订单管理与履约状态
- **为什么需要**：订单是交易事实的载体，必须可靠查询、受控流转、完整留痕。
- **设计逻辑**
  - 订单/付款/履约三个状态维度分离，机器状态是唯一事实，页面只做文案映射。
  - 保存下单时商品/价格/语言/地址快照；状态转换受限并记历史。
  - Shipment 与订单分开建账，支持分批发货，累计不超订量；已发包裹不可被普通编辑覆盖。
  - 地址仅在未发货、经授权、重新校验区域/费用后可改；发货后走承运商而非直接改单。
  - 退款/退货/换货走 M16 案件，不覆盖原订单/付款历史。
- **协作**：依赖 M00/M08/M09；被 M13（通知）、M14（报表）订阅事件。

### M08 付款方式与交易记录
- **为什么需要**：资金入账是最高风险环节，必须可替换、可验签、可对账、不产生资损。
- **设计逻辑**（资金类底线最集中的模块）
  - 适配器框架接入获批支付方式；密钥放密钥管理服务，凭证保存后不再明文展示。
  - 回调验签 + 幂等 + 重放保护；支付状态以可信服务端事件/查询更新。
  - `unknown` 状态按 1/5/15/30 分钟主动复查，仍未知进人工队列；**不将未知改为失败、不释放占位、不重复付款**。
  - 对账按支付/退款/结算行/COD 分别核对，区分"支付成功"与"已结算"；差异分类 + 人工核实 + 审计；导入不自动改写已确认事实；重复文件识别阻止重复入账。
- **协作**：依赖 M06/M07/M01；受服务商账户/凭证就绪度影响最大（上线阻塞项）。

### M09 配送与运费规则
- **为什么需要**：把运费计算从交易代码里解耦，让商家按区域/门槛自配。
- **设计逻辑**
  - 结账按地址选唯一有效规则，费用构成对顾客可见并保存快照；不可配送地址不能下单。
  - 首期人工履约 + 多包裹记录；承运商 webhook 回传先验签、按 eventId 幂等、只认已 dispatch 包裹，`delivered` 由服务端推进履约且**不改付款状态**。
  - 分批发货数量合计不超订单，已发包裹不可被普通编辑覆盖。
- **协作**：依赖 M01/M07；被 M06 结账调用费率报价。

### M12 库存与预警
- **为什么需要**：防超卖、保证可售数准确，并与资金/履约状态联动。
- **设计逻辑**
  - 单仓、现货/预留/可售三分量 + 不可改写流水；并发原子校验防超卖。
  - 下单原子预留；线上待付款默认 30 分钟，到期**先查渠道**，明确失败/取消才释放，未知保持预留并告警。
  - 发货按包裹数量扣减；盘点导入必须生成逐 SKU 调整流水，不直接覆盖库存表。
  - 退货经 M16 收货质检后才恢复可售库存。
- **协作**：依赖 M03；被 M06/M07 消费预留契约；由 M08/M09/M16 事件触发流水。

## 运营与增长

### M10 顾客与会员
- **为什么需要**：在"不强制注册"前提下提供会员运营与合规的顾客资料处理。
- **设计逻辑**
  - 电话/邮箱验证后才可关联或登录会员；不按姓名自动合并；OTP 只存摘要，通用错误文案防账户枚举。
  - 积分：订单完成发放、取消/退款按比例幂等扣回、兑换占用/撤销可追踪；规则变更只影响未来，历史流水保留规则版本。
  - 隐私请求状态机完整（received→…→completed），处理前身份核验；未核验不得导出/删除；不改写交易事实；逾期显示负责人与时长，不静默完成。
  - 营销同意与交易通知分离，验证码不作营销授权；OTP 故障不阻断访客结账。
- **协作**：依赖 M00/M07/M08/M13；为 M11 会员专属券提供已验证身份。

### M11 优惠券与促销
- **为什么需要**：在不破坏交易一致性的前提下提供可配置的促销工具。
- **设计逻辑**
  - 服务端校验时效/次数/范围/会员资格/叠加策略；百分比用 bps、half-up；最低消费基价口径明确。
  - 默认每单一个优惠码、不叠加；事务原子预占额度防超发；核销四态（可用/预占/已核销/已释放）关联订单与批次。
  - 结果未知的线上付款不释放可能仍成功的额度；退款/退货是否返券由客户配置。
  - 保存优惠规则版本与分摊快照，后续改规则不改历史订单金额。
- **协作**：依赖 M00/M07/M10/M13；M06 调其预占契约。

### M13 订单通知与客服资料
- **为什么需要**：把订单关键节点可靠触达顾客，并与营销消息隔离。
- **设计逻辑**
  - 只用获批渠道与模板；交易通知与营销通知分开，密钥不明文。
  - 幂等键 = 业务事件 + 接收目标 + 模板版本；业务事务提交后才入队，失败不回滚订单。
  - 生产语言缺已批准模板时不回退其他语言，标记配置失败并告警；交易模板就绪是开店门槛。
  - 日志只留脱敏目标与状态，不留 OTP 明文。
- **协作**：依赖 M01/M04/M07 事件契约；服务 M10 OTP 与 M11 营销消息。

### M14 数据统计与分析
- **为什么需要**：让经营者同时看清"经营结果"与"访问转化"，但两者口径绝不能混。
- **设计逻辑**
  - **两套数据严格分离**：订单/支付/退款账本是金额权威；访问分析是匿名事件，不能反向决定财务数据。
  - 指标口径词典化：下单额/已收额/净销售额/实收等分别定义，禁止合并改名；多币种不相加。
  - 事件不含 PII，用随机会话/交互 ID 关联；禁止设备指纹；按市场配置告知/同意。
  - P1 陈列分析：曝光（50% 可见持续 1 秒）、点击、加购、服务端订单归因、净实收分摊口径都有明确定义；预览/员工/沙箱/测试数据排除；缺数据显示"采集状态"而非 0。
  - 定制主题必须走统一埋点 SDK/契约，保证跨主题可比；外部分析连接器故障不阻塞商城。
- **协作**：依赖 M00/M01/M02/M03/M06/M07/M08/M11/M12 及市场合规规则。

## 售后

### M16 售后、取消与退款
- **为什么需要**：把取消/退款/退货/换货收敛到一个可审计流程，且每个动作都能追溯原订单与资金/库存流水。
- **设计逻辑**
  - 案件与订单解耦：一订单可多案件，但累计数量/退款不超上限；不改写已确认的订单/支付快照。
  - 角色分工明确（店主/客服/财务/仓库权限矩阵）；退款限额、双人审批可配。
  - 金额：仅对已实收且未退金额退款，累计不超可退余额；服务端创建退款存幂等键与渠道号；**退款成功 ≠ 案件完成**（还需收货/补发才关案）。
  - COD 未收款取消不虚构退款；已收 COD 通过人工渠道记录。
  - 库存：退回商品收货质检前不增加可售库存，质检后按重新入库/损坏/冻结/报废分别产生流水。
  - 状态机覆盖退款失败/处理中，可对账、可安全重试；顾客通知失败不丢案件或退款记录。
- **协作**：依赖 M00/M07/M08/M09/M12；通知走 M13、会员积分联动走 M10（可选）、汇总进 M14。

## 结语：模块设计的一致性

17 个模块看似分散，实则共享同一套设计语法：

- **权威在服务端**（M06/M08/M12），**快照保历史**（M03/M07/M08/M11/M16）；
- **预占—核销—释放**贯穿库存/优惠/积分/退款；
- **状态机 + 幂等 + 对账**守住资金与交易底线；
- **权限分级 + 审计**覆盖所有敏感动作；
- **白名单与阻断**（区块注册、缺译、市场审核、模板缺失）替代"静默容错"，用明确的失败换取可诊断性。

理解这五条，就理解了这套产品绝大多数具体规则的来龙去脉。
