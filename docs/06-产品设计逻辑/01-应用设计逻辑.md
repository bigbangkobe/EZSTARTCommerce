# 应用设计逻辑（4 个子应用）

> 本文展开 [设计逻辑总览](00-设计逻辑总览.md) 第 3.1 节：逐一讲清 4 个子应用"为什么存在、负责什么、不负责什么、与谁协作、关键取舍"。
> 技术实现契约见 `03-开发文档/DEVELOPMENT_SPEC.md`、`API_SPEC.md`；模块规则见 [02 模块设计逻辑](02-模块设计逻辑.md)。

---

## 总览：四个应用的分工

```
        ┌──────────────┐        ┌──────────────────┐
        │  admin 后台   │        │ storefront 客户前台│  （均可同仓不同应用）
        │  商家操作入口 │        │  顾客购物界面     │
        └──────┬───────┘        └────────┬─────────┘
               │ 会话认证 /admin         │ 公开读 /api/v1
               └──────────┬──────────────┘
                          ▼
                 ┌──────────────────┐        ┌───────────────┐
                 │   api 单体        │ ──outbox──▶ │  worker 异步  │
                 │  领域规则/交易权威│        │ 通知/定时/任务│
                 └────────┬─────────┘        └───────────────┘
                          ▼
                 ┌──────────────────┐
                 │ PostgreSQL（单实例）│   + 对象存储 + 密钥管理
                 └──────────────────┘
```

核心设计原则：**只有 `api` 能改交易数据**；`admin`/`storefront` 只是不同形态的客户端，`worker` 只做可重试的后台任务。这保证了交易规则的唯一权威来源。

---

## 1. `apps/api` — 业务 API（NestJS 模块化单体）

### 为什么存在
它是全部领域规则与交易数据的**唯一权威执行点**。所有"服务端裁定"（重算价格、预留库存、核销优惠、确认支付、状态流转）都发生在这里，客户端和 worker 都必须经过它。

### 负责什么
- REST `/api/v1` 接口，OpenAPI 为契约与类型生成来源（`packages/contracts`）。
- 两大访问域严格分开：后台 API（会话认证 + RBAC + 审计）与 Storefront 公开读接口（只返回已发布/可售数据）。
- 16 个领域模块（identity-admin / catalog / cart-checkout / orders / payments-reconciliation / …）通过公开应用服务与事件协作。
- 幂等键、ETag 版本冲突、稳定错误码、请求 ID 贯穿所有写接口。

### 不负责什么
- 不做品牌视觉、不做页面渲染。
- 不直连客户前台代码；前台通过生成的客户端调用它。

### 关键设计取舍
| 取舍 | 决策 | 理由 |
|---|---|---|
| 单体 vs 微服务 | 模块化单体 | 首期规模下避免分布式复杂度；靠模块边界纪律（禁止跨域直接改表）维持清晰度 |
| ORM 边界 | Prisma 7 + 显式 SQL/事务 | 金额、库存、优惠、幂等写入必须在数据库事务内；复杂行锁用参数化 SQL；不用 ORM 回调实现状态机 |
| 第三方调用 | 不在 DB 事务中等待网络 | 支付/邮件超时不阻塞事务，改用 outbox + 补偿 |
| 破坏性变更 | 新增主版本 | `/api/v1` 同主版本只做向后兼容新增；客户前台锁定 API 主版本 |

### 协作关系
- 被 `admin`、`storefront` 调用；向 `worker` 投递 outbox 任务；消费 `worker` 的回调结果（如支付查询、定时发布）。

## 2. `apps/admin` — 商家管理后台（Next.js + React）

### 为什么存在
商家运营人员日常维护商品、订单、会员、促销、内容、报表的统一入口。它是"受控的后台配置"这一半世界的载体。

### 负责什么
- 覆盖 M00–M16 的后台页面（登录/MFA、设置、商品、内容/陈列、订单、售后、会员、优惠、库存、报表、审计、运维等）。
- 稳定的导航 + 列表/表单/详情一致模式；危险操作二次确认；每页包含加载/空/校验错误/服务失败/权限不足/成功反馈。
- RBAC 菜单与操作控制（API 直接访问同样受控，前端控制只是体验层）。

### 不负责什么
- 不自行决定是否允许操作——所有敏感动作由服务端权限码校验；前端不做交易金额的最终计算。
- 不承载顾客购物流程（那是前台的事）。

### 关键设计取舍
| 取舍 | 决策 | 理由 |
|---|---|---|
| 权限校验位置 | 服务端为准，前端只做展示 | 防止绕过 UI 直接调 API；权限收紧后下次请求立即生效 |
| 敏感操作 | 二次确认 + 审计 + 可配双人审批 | 退款/导出/权限变更误操作代价高 |
| 审计能力 | 只读取、不可编辑删除 | 保证追责链完整 |
| 多语言 | 简/繁/英分别验证长文案溢出 | 后台也要面向三语运营 |

### 协作关系
- 调用 `api` 后台接口；配置变化（如内容/陈列发布）通过 `api` 影响前台；操作写入审计。

## 3. `apps/storefront-mrinhk` — 客户专属前台（首个客户 IN先生）

### 为什么存在
它是"客户前台独立定制"这一设计的具体落地样板。品牌、页面结构、视觉、购买交互都属客户资产，与通用核心解耦。

### 负责什么
- 品牌化页面：日式极简卡片风格、品牌红色点缀、默认繁体中文（简中/英文文案结构预留）。
- 页面：首页（Hero/关于/精选商品/WhatsApp CTA）、商品、联络页等，按客户批准的页面清单实现。
- 通过 API 读取已发布内容与可售商品；接入 SEO 元数据、语言 URL、sitemap。

### 不负责什么
- **不复制业务规则、不直连数据库、不自行计算价格/库存/订单金额**——一律走服务端核心。
- 不与其他客户共享发布节奏；它的发布不影响别人。

### 关键设计取舍
| 取舍 | 决策 | 理由 |
|---|---|---|
| 定制程度 | 独立应用、可改页面结构与交互（非换色换标） | 品牌体验必须自由，但要付出单独设计/开发/验收成本 |
| 数据来源 | 只调稳定 API + 主题区块契约 | 核心升级不覆盖客户前台；API 主版本锁定保证兼容 |
| 交易降级 | 接口不可用时退回主题默认精选 | 陈列是增强，不能成为首页单点故障 |
| 索引控制 | 预览/购物袋/结账不索引；404 先查 301 | 避免空壳页被收录、旧地址死链 |

> 说明：项目实际客户前台为 `storefront-mrinhk`；开发规格中的 `storefront-reference/` 指通用参考前台基线，二者是"通用基线 vs 客户定制"的关系。

### 协作关系
- 只读调用 `api` 的 Storefront 接口；上报匿名分析事件（M14 统一埋点契约）；发布版本由 `api` 的内容发布计数器（`cr-N`）标识。

## 4. `apps/worker` — 身份通知 Worker（NestJS 独立进程）

### 为什么存在
把可重试、可能慢、可能失败的后台工作从请求链路里剥离，保证下单等主流程不被第三方通知拖慢或阻断。

### 负责什么
- 处理异步任务：订单/状态通知发送、内容定时发布检查（每 15 秒）、密码重设邮件、到期任务等。
- 基于 PostgreSQL outbox + job 表；任务具备租约、重试、死信、幂等。
- SMTP 配置与邮件投递、验证边界。

### 不负责什么
- 不做交易决策（不改订单金额/支付状态）；不直接接受客户端请求。
- 不在发送失败时回滚业务事务（通知失败只记失败状态并告警）。

### 关键设计取舍
| 取舍 | 决策 | 理由 |
|---|---|---|
| 队列选型 | PostgreSQL outbox + job，不依赖 Redis | 首期不引入额外中间件；权威状态与业务在同一 DB，事务性投递 |
| 幂等键 | 业务事件 + 接收目标 + 模板版本 | 重复 webhook/队列消费不重复发送 |
| 失败处理 | 失败可重试 + 人工重发留审计 | 通知可靠性与可追责 |
| 事务边界 | 业务事务提交后才建通知任务 | 避免通知先于业务落账 |

### 协作关系
- 消费 `api` 投递的 outbox 任务；回写任务状态；定时发布完成后由 `api` 推进内容版本。

---

## 5. 应用间的三条协作主线

1. **下单主线**：storefront → api（服务端报价 + 幂等建单 + 预留库存/优惠）→ outbox → worker（订单通知）。
2. **内容发布主线**：admin（编辑草稿）→ api（发布快照 + 推进 `cr-N`）→ storefront（只读快照渲染 + 埋点）→ worker（定时发布）。
3. **后台管理主线**：admin（会话 + RBAC + MFA）→ api（权限校验 + 审计）→ 变更通过 api 影响各域数据。

三者共同体现同一逻辑：**客户端负责交互与展示，API 负责权威与一致，Worker 负责可靠与解耦**。
