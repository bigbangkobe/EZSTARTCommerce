## 1. 一句话产品定义与设计原点

**EZSTARTCommerce 是一套"可重复交付、逐客户独立部署"的通用电商核心 + 商家后台模板，客户前台按各自品牌单独定制。**

设计原点来自三个被反复确认的约束，它们决定了后面几乎每一条规则：

1. **不是 SaaS**——不建共享多租户控制面、不做跨店数据池、不做平台订阅计费。每家商家一套独立应用/数据库/媒体/密钥/域名/备份。
2. **交易由服务端裁定**——浏览器传来的价格、折扣、库存、运费一律不可信，服务端重算并以事务/幂等方式落账。
3. **通用核心与行业/客户差异分离**——烟草只是首个行业配置包，客户前台独立版本发布；核心升级不覆盖商家配置与数据。

> 这三点是理解全部设计决策的"第一性原理"。凡是看起来"多此一举"的校验、快照、状态拆分，几乎都能回溯到这三条。

## 2. 产品定位决策：为什么是"独立实例 + 定制前台"

| 设计选择 | 理由 | 带来的代价（已被接受） |
|---|---|---|
| 一商家 = 一独立实例（DB/媒体/密钥隔离） | 数据隔离最简单可靠，避免跨租户串数据；交接与销毁边界清晰 | 无法共享运营数据、无法做平台级分析，运维成本随客户数线性增长 |
| 后台与交易核心复用、前台独立定制 | 通用能力（商品/订单/支付/库存）值得复用；品牌体验必须因客户而异 | 客户前台需单独设计/开发/验收/发布，成本单独估算 |
| 模块化单体（而非微服务） | 首期规模下，清楚分域的单体 + 独立 worker 足够，避免提前拆分带来的分布式复杂度 | 单体内必须靠纪律维持模块边界（公开服务/事件，禁止跨域直接改表） |
| 不做页面搭建器，只做"主题注册的区块配置" | 任意拖拽/自定义代码会击穿安全与升级边界；有限区块可维护 | 客户要全新页面行为时必须走定制开发 |

这一组决策把产品切成两个世界：**受控的后台配置**（商家自助、服务端校验、可审计）与**可变的客户前台**（品牌自由、但只通过稳定 API 读数据、不自行计算交易金额）。

## 3. 系统全景：由哪些"产品"组成

### 3.1 四个技术子应用

| 应用 | 角色 | 设计要点 |
|---|---|---|
| `apps/api` | NestJS 模块化单体，领域规则与交易权威所在 | 唯一能改交易数据的地方；REST `/api/v1` + OpenAPI 契约；分域鉴权（后台会话 vs 前台公开读） |
| `apps/admin` | Next.js 商家后台 | 所有敏感动作经服务端授权；RBAC + MFA + 审计；页面状态完整（加载/空/错/权限不足） |
| `apps/storefront-mrinhk` | 首个客户（IN先生）专属前台 | 品牌独立、独立版本；只调 API、不复制业务规则、不直连数据库；价格/库存/订单一律服务端 |
| `apps/worker` | 独立异步任务进程 | 处理通知、定时发布等；基于 PostgreSQL outbox + job 表；租约/重试/死信/幂等 |

展开见 [01 应用设计逻辑](01-应用设计逻辑.md)。

## 4. 贯穿全局的"横切设计逻辑"

这些规则不属于任何单一模块，而是所有模块共同遵守的约束——它们是这套设计真正的"骨架"。

### 4.1 金额与交易一致性（资金类底线）

- **服务端定价**：价格、折扣、运费、税费、总额全部服务端重算；购物车报价默认 15 分钟有效，变化后需顾客二次确认。
- **整数最小货币单位**：金额以最小单位整数 + ISO 币种存储，禁止浮点；百分比用 basis points（100 bps = 1%），half-up 舍入。
- **快照不可变**：订单、支付、退款、运费、商品规格、下单语言都保留交易时快照，后续改商品不回写历史订单。
- **幂等三件套**（资金操作强制）：创建订单/付款/退款、库存调整、导入执行、结算确认、批量发券都接受 `Idempotency-Key`；webhook 验签 + 幂等 + 重放保护；重复回调不重复入账。
- **对账不改写事实**：结算文件导入只做匹配与差异分类，不因导入自动修改已确认付款/退款事实。
- **资损监控点**：支付状态 `unknown` 不得当成失败、不得释放库存/优惠占位；只有渠道明确失败/取消才释放。

### 4.2 状态机与状态一致性

- 订单、付款、履约、售后各有独立状态机，机器状态是唯一事实，页面只做本地化文案映射，不得自行增删合并状态。
- 关键分流：COD 下单为 `awaiting_confirmation`/`cod_due`，后台确认后 `confirmed`；线上订单只有服务端确认收款后才 `confirmed`。
- 状态转换受限且记入历史；退款结果与案件完成是不同状态（还需收货/补发的继续履约后才关案）。
- 状态单向流转 + 回调/主动查询双通道，防状态回跳。

### 4.3 库存、优惠与权益的"预占—核销—释放"

这是一个反复出现的通用模式，横跨 M06/M11/M12/M16：

```
下单时原子预占 → 支付结果明确 → 成功则核销 / 失败或取消则释放
                 → 结果未知则保持预占并告警（绝不误释放）
```

- 库存：单仓、现货/预留/可售三分量 + 不可改写流水；并发原子校验，防超卖。
- 优惠：事务原子预占额度，避免超发；核销状态区分可用/预占/已核销/已释放。
- 积分（M10）：订单完成后发放，取消/退款按已确认比例幂等扣回。
- 退款/退货（M16）：退款额不超可退实收；退回商品收货质检后才恢复可售库存。

### 4.4 权限与安全模型

- **最小权限 RBAC**：角色→权限码，每个新增后台 API/导出/异步下载都必须有 permission code；顾客账号与后台账号分离。
- **高权限角色 MFA**：店主/管理员必须启用 TOTP + 一次性恢复码；登录限速、会话空闲/绝对期限、会话撤销。
- **敏感动作分级**：退款、改价、导出、隐私请求、权限变更做权限校验 + 二次确认 + 审计；高风险金额可配双人审批。
- **审计只增不改删**：应用层不提供审计编辑/删除；日志不记录密码、OTP、支付密钥、完整银行资料。

### 4.5 隐私与数据最小化

- 访客可全程购物结账；会员是自愿、邮箱 OTP、不设密码。
- 顾客身份按已验证联系方式关联，不按姓名自动合并；营销同意与交易通知分开记录。
- 分析事件不含姓名/电话/邮箱/地址/支付凭证；用随机会话/事件 ID 关联，禁止设备指纹。
- 个人资料请求（访问/导出/更正/删除/匿名化）需身份核验；不改写订单/支付/售后等交易事实。

### 4.6 多语言与内容发布

- 简体中文/繁体中文/英文独立存储，不互相伪装；发布要求启用语言必填内容齐全，缺译阻断而非静默回退。
- 草稿与发布分离：保存草稿不改变公开地址；发布固化为不可变快照，前台只读快照；跨语言原子切换。
- 版本/回滚/定时：版本历史不可覆盖；回滚用历史快照建新版本；定时失败保留线上版本并告警。

### 4.7 可靠性与异常韧性

- 外部服务（支付/邮件/短信/物流）有超时、重试、服务端结果查询和人工补偿入口；**禁止在数据库事务中等待第三方网络请求**。
- 异步任务基于 outbox + job 表，具备租约/重试/死信/幂等；通知在业务事务成功提交后创建，失败不回滚订单。
- 未知优先：支付未知保持占位、缺译阻断、埋点缺失显示"采集状态"而非 0、接口不可用前台退回默认精选而非空白。

## 5. 端到端主流程（主线串联）

| 流程 | 关键链路 | 设计要点 |
|---|---|---|
| 实例开通 | 部署 → 初始化 → 配置 → 测试订单 → 备份/升级检查 → 上线 | 两实例隔离验收、密钥不进仓库、市场合规由商家审核 |
| 上架商品 | 草稿 → SKU/价格/库存 → 三语 → 预览 → 校验 → 发布 | 缺译阻断、被订单引用的商品只归档不删除 |
| 访客下单 | 浏览 → 选 SKU → 购物袋 → 服务端报价 → 联系/配送 → 幂等建单 → 状态分流 | 服务端重算、支付返回不作到账依据 |
| 订单履约 | 新单队列 → 审核 → 备货 → 分批发货 → 签收/异常 → 完成 | 包裹与订单分开建账、累计发货不超订量 |
| 售后 | 申请 → 核实 → 审核 → 收货质检 → 退款/补发 → 库存/指标更新 → 关案 | 退款结果 ≠ 案件完成；质检前不恢复库存 |

流程细节见 [02-设计文档/WORKFLOWS.md](../02-设计文档/WORKFLOWS.md)。

## 6. 设计决策索引（"为什么这样设计"速查）

| 决策 | 采纳方案 | 被否决的替代 | 决策依据 |
|---|---|---|---|
|  tenants 模型 | 独立实例 | 共享多租户 SaaS | 隔离可靠、交接清晰、合规边界明确 |
| 交易金额来源 | 服务端重算 + 快照 | 信任前端报价 | 防篡改、可审计、可对账 |
| 金额存储 | 整数最小单位 | 浮点 | 精度与舍入一致性 |
| 服务拆分 | 模块化单体 + worker | 微服务 | 首期规模、避免分布式复杂度 |
| 页面构建 | 主题注册区块配置 | 任意拖拽建站器 | 安全与升级边界可维护 |
| 会员登录 | 自愿邮箱 OTP、无密码 | 强制注册 + 密码 | 访客结账优先、隐私最小化 |
| 异步机制 | PostgreSQL outbox + job | 依赖 Redis | 首期不引入额外中间件、权威状态在 DB |
| 缺译处理 | 阻断发布 | 静默回退/机器翻译 | 避免展示错误语言 |
| 支付未知 | 保持预占 + 告警 | 当成失败并释放 | 防资损、支持支付恢复 |
| 分析口径 | 订单/支付账本为权威 | 浏览器购买事件 | 财务数据可信、可对账 |
