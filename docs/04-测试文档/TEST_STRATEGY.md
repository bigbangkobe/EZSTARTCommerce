# EZSTARTCommerce 测试策略与质量门禁

2026-10-19 工程入口：`pnpm check` 运行契约验证、生成类型漂移检查、TypeScript 检查、身份规则/客户端单元与 HTTP 冒烟测试。范围与尚未实现的数据库/身份联调见 [R1 工程说明](../03-开发文档/R1_ENGINEERING_PROGRESS.md)；不能将这些结果视为全部发布门禁通过。

> 版本：1.0（开发前质量规格）  
> 当前状态：策略与场景已定义；可执行测试需随代码按模块实现。当前仓库还没有应用代码、测试框架配置或可运行的自动化测试，因此不能称为“单元测试已完成”。  
> 配套：[API 接口契约](../03-开发文档/API_SPEC.md)、[测试用例矩阵](TEST_CASES.md)、[生产就绪验收](PRODUCTION_READINESS_ACCEPTANCE.md)。

## 1. 目标与测试原则

- 每个需求都要关联模块 ID、API operation、权限码和至少一个通过/拒绝/边界用例。
- 先测领域规则和数据一致性，再测 API/页面交互；关键交易必须用全链路场景证明业务闭环。
- 金额、订单状态、支付状态、库存和优惠额度以数据库及领域服务为权威，不能仅测 UI 显示。
- 正常、拒绝、并发/重复、外部超时/未知、权限拒绝和恢复路径都要有覆盖。
- 同一套业务核心在每客户独立部署；测试隔离、备份恢复和配置差异也属于质量范围。
- 测试不得连真实收款、真实短信/邮件营销名单或生产客户数据；用沙箱、stub 和合成数据。

## 2. 测试分层

| 层级 | 测什么 | 主要工具/位置（实现时选定） | 完成证据 |
|---|---|---|---|
| 静态检查 | 格式、lint、TS 类型、安全依赖和秘密扫描 | pnpm workspace CI | CI 结果，无新增高危依赖/秘密 |
| 单元测试 | 纯领域规则、状态机、金额/优惠/配送/积分计算、输入校验 | Vitest；domain/application 包 | 每个规则有正向、边界、拒绝案例；确定性且隔离外部 I/O |
| API/数据库集成 | Nest 模块、PostgreSQL 事务、唯一约束、行锁、迁移、outbox、幂等 | Vitest + 临时 PostgreSQL/Compose | 真实数据库验证并发、回滚、重复投递及版本迁移 |
| 契约测试 | OpenAPI 请求/响应、权限、生成客户端兼容、provider adapter | OpenAPI validator + contract tests | 规范与实现一致；兼容性检查通过 |
| API 功能测试 | 认证、权限、正常/错误 HTTP、字段遮蔽、分页、限速 | API integration/e2e harness | operation 级状态码、错误码和副作用均正确 |
| 前端组件/页面测试 | 表单校验、加载/空/错误/无权限态、响应式、三语 | Testing Library + Vitest | 关键页面交互与可访问性基础断言通过 |
| 浏览器端到端测试 | 顾客站和管理后台真实浏览器旅程 | Playwright；桌面与移动 viewport | 关键路径可重复运行，无真实外部账户 |
| 服务商适配器测试 | COD、线上支付、邮件/短信等沙箱和签名样例 | provider sandbox/stub + contract fixture | 签名、超时、重复、未知、重试和降级行为可证实 |
| 性能/容量测试 | 目录读取、结账、后台列表、报表、导入任务、媒体 | 具名负载脚本；独立非生产环境 | 满足开发规格目标；记录数据量、硬件、p75/p95 |
| 安全与隐私测试 | 登录/MFA/CSRF、越权、注入、速率限制、PII/秘密泄漏 | 自动化检查 + 定向人工验证 | 高风险问题关闭；敏感字段/日志遮蔽有证据 |
| 部署/恢复测试 | 全新安装、升级、备份、数据库+媒体恢复、回滚 | 与客户交付 Compose 版本一致的隔离环境 | 记录镜像、迁移版本、RPO/RTO 实测及校验结果 |
| 业务验收/UAT | 店铺运营和顾客场景、语言、内容、客户定制前台 | 由业主/运营按签字用例执行 | 用例结果、缺陷、例外和签字记录 |

## 3. 单元测试边界

至少针对以下纯规则建立 unit suites：

- 金额计算、币种精度、折扣分摊、退款可退余额和舍入余数分配。
- 优惠有效期、范围、限制、占位/核销/释放转换。
- 库存 `available = on_hand - reserved`、预留过期状态和流水约束。
- 商品发布资格、三语必填、市场可售和动态陈列稳定排序。
- 订单、支付、退款、发货、售后各状态机的允许/拒绝转换。
- 配送区域命中、运费/免运门槛和地址变更价格差额判定。
- OTP 期限、尝试次数、冷却规则；会员积分获取/冲回幂等计算。
- 报表日期边界、店铺时区、营业日和口径过滤规则。
- 权限策略评估、脱敏策略、错误码映射和导入行校验。

单元测试不得 mock 被测的核心计算本身。数据库唯一约束、事务、锁和迁移不属于 unit 替代范围，必须由集成测试覆盖。

## 4. API/功能测试规则

- 对每个 OpenAPI operation 至少覆盖成功、未认证/无权限、字段错误、版本或状态冲突；交易写操作再测幂等和副作用。
- 验证 HTTP status、稳定 `error.code`、响应 schema、审计记录、领域数据变更和异步任务/outbox。
- 读写权限分别测试；手工构造直接 API 请求，不能只验证菜单/按钮隐藏。
- 第三方服务须可注入：成功、拒绝、超时、连接中断、重复回调、乱序事件和未知状态。
- 对异步 API 验证先返回 job 状态、进度/失败可查、重试限制和最终状态；不能以 UI toast 代替后台任务完成。

## 5. 全功能链路回归套件

至少维护以下 10 条稳定回归旅程；每次发布候选包均运行关键路径：

1. 首次初始化店铺 → 创建员工/角色/MFA → 三语与市场配置 → 初始化支付/配送。
2. 新建商品/三语/SKU/图片 → 库存阈值 → 发布 → 分类/搜索前台可见。
3. 配置首页区块/手工选品与动态排序 → 手机/桌面预览 → 定时发布 → 前台读取新版本 → 回滚。
4. 标准 CSV 导入 → 校验预览 → 纠错 → 执行 → 行级结果/错误报告/商品前台验证。
5. 顾客访客购物 → 优惠 → 地址/运费报价 → 价格变化重新确认 → 幂等创建订单。
6. COD 订单 → 后台确认/拣货 → 分包裹发货/签收 → 人工收款 → 通知与报表。
7. 线上支付沙箱 → 签名回调 → 重复/乱序/延迟/未知支付处理 → 查询恢复 → 结算对账。
8. 会员邮箱 OTP → 会员权益/积分预占 → 完成订单入账 → 部分退款按比例冲回。
9. 取消/售后申请 → 授权审批 → 退货收件质检 → 退款 → 可售/损坏库存分类处理。
10. 隐私导出/删除请求 → 身份核验 → 审批/处理 → 审计；部署备份 → 新环境恢复 → 媒体/交易校验。

## 6. 测试数据与环境

- 使用合成数据；默认基准语言 `zh-CN`、`zh-HK`、`en`，并至少含一个多规格商品、一个缺译草稿、可售/缺货商品、市场禁售商品。
- 测试金额使用整数最小单位；固定时钟/时区以验证有效期、日界线、夏令时和定时发布。
- 通过可重置的测试商店数据库运行集成测试；每个用例独立 fixture/事务或可重复清理。
- 支付、邮件、对象存储等外部服务默认 stub；需要验证行为时使用隔离沙箱账号和测试 webhook 秘钥。
- 并发用例必须确实并行提交并检查最终数据库账本，不用顺序模拟代替。
- 浏览器测试至少覆盖当前支持的桌面 Chromium 与窄屏移动 viewport；每个客户额外验证已签署的专属前台目标设备/浏览器。

## 7. 通过门槛与缺陷等级

### 7.1 发布门禁

1. 所有静态检查、构建、迁移检查和 PR 必跑 unit/integration suites 通过。
2. 所有 P0/P1 测试用例通过；P0 无已知未解决缺陷。风险例外由产品负责人书面签收并定复核日期。
3. 订单/支付/退款/库存/优惠账本的关键不变量和并发用例通过。
4. OpenAPI schema 与实现、生成客户端同步；新增 operation 权限和审计测试通过。
5. E2E 核心旅程可重复通过；浏览器失败具备 trace/screenshot/log，且不把敏感数据放入附件。
6. 安全扫描无未处置的高危/严重项；备份恢复和部署升级路径按版本完成验收。
7. 目标客户三语、支付/配送参数、隐私和监管配置须另按该实例签字，不由模板测试结果代替。

### 7.2 严重级别

| 级别 | 示例 | 发布处置 |
|---|---|---|
| P0 阻断 | 越权付款/退款、数据跨实例暴露、重复扣款、超卖或不可恢复数据丢失 | 禁止发布 |
| P1 严重 | 关键购物/下单/后台运营主链路无法完成、金额错误、无法安全恢复 | 禁止生产发布 |
| P2 一般 | 有替代路径的非关键功能错误、局部显示/导出问题 | 评估并登记修复版本 |
| P3 轻微 | 不影响交易的视觉或文案问题 | 进入普通待办 |

## 8. 覆盖率和可追溯性

覆盖率作为诊断，不以百分比替代规则覆盖。初始参考门槛：核心 domain/application 语句覆盖率 ≥ 80%，分支覆盖率 ≥ 75%；关键金额、状态机、权限和幂等分支必须逐分支有用例。所有差异需有理由并记录。PR 描述关联需求/模块、API operation、`TC-*`、迁移和风险。

测试执行记录保存：版本/commit、环境、数据 fixture 版本、运行人/时间、测试套件与用例结果、失败附件、缺陷链接、批准例外。生产顾客资料不得复制到自动化测试环境或 trace。

## 9. 开发阶段落实顺序

- R1 工程骨架：CI、测试命令、临时数据库、测试数据工厂、OpenAPI 校验和报告格式。
- 每个模块开发 PR 同步提交 unit + integration/API + 对应测试用例状态；不把测试全部推迟到 R6。
- 每个发布批次建立对应 Playwright 链路；跨模块 R3/R4/R5 全链路回归并持续运行。
- R6 生产就绪：跑完整回归、性能/安全验证、部署/恢复和客户 UAT，形成签字证据包。

具体用例编号和前置/预期见 [测试用例矩阵](TEST_CASES.md)。
