# M16 售后、取消与退款

**优先级：**P0 基础后台案件与退款记录；前台自助申请为 P1 条件能力。  
**初步开发估算：**10–16 人日（含基础管理页、状态与支付/库存联动；不含支付服务商手续费和高级退换货物流集成）

## 产品目标

让商家在一个可审计的后台流程中处理订单取消、退款、退货和换货。每个售后动作关联原订单、订单行、付款流水和库存流水；保持顾客不需要注册或登录。

## 首期范围

- 后台售后案件列表、筛选、详情、备注、附件引用和状态时间线。
- 订单取消申请/内部发起、审核、拒绝、原因记录。
- 全额或部分退款申请、权限审批、服务商退款/人工线下退款记录。
- 退货/换货案件登记、收货状态、质检结论、库存处置记录。
- 订单支付金额、累计已退、可退款余额校验。
- COD 订单区分未收款、已收款、已退回；未收款订单不虚构支付退款。
- 交易通知及失败补偿记录。
- 前台无需账户的自助申请作为条件能力：经短期验证链接/验证码确认订单后，仅展示必要字段。

## 角色与权限

| 角色 | 查看案件 | 建立/编辑案件 | 审批退款 | 执行退款 | 修改库存处置 |
|---|---:|---:|---:|---:|---:|
| 店主 | 是 | 是 | 是 | 是 | 是 |
| 客服 | 是 | 是 | 是（按限额） | 否/按授权 | 否 |
| 财务 | 是 | 否/备注 | 是 | 是 | 否 |
| 仓库 | 受限字段 | 更新收货/质检 | 否 | 否 | 仅建议 |
| 商品/分析 | 否或聚合 | 否 | 否 | 否 | 否 |

退款限额、双人审批和查看完整顾客资料权限可配置；所有敏感动作记录操作者、金额、原因、前后状态与外部交易号。

## 页面与字段

### M16-A 售后案件列表：/admin/aftersales

筛选项：案件号、订单号、案件类型、状态、付款方式、创建时间、负责人。列表列：案件号、订单、顾客脱敏标识、类型、申请/批准金额、支付状态、履约状态、当前处理人、更新时间。批量操作仅允许分派或导出，不批量执行退款。

空态提供“从订单创建售后”；无权限时不显示顾客资料；失败任务提供安全重试入口。

### M16-B 案件详情：/admin/aftersales/{id}

- 顶部：案件号、原订单链接、类型、状态、优先级、负责人。
- 订单摘要：下单商品快照、已付/已收金额、累计退款、可退余额、配送状态。
- 案件内容：原因、顾客说明、申请商品/数量、期望处理方式、附件索引。
- 处理区：审核通过/拒绝、要求补充资料、录入退货追踪、收货质检、录入退款、补发/换货关联单。
- 时间线：每次状态、审批、支付退款、库存处置、通知和备注。
- 高风险按钮二次确认，展示对象、金额、币种、退款渠道和不可撤销提示。

### M16-C 从订单新建

从订单详情发起，默认带入顾客、订单行、付款和物流快照；选择取消、退款、退货或换货类型。服务端计算可选数量和最大退款额，禁止超额。不得更改原订单行历史快照。

## 案件状态

建议状态：
draft → submitted → under_review → approved / rejected / needs_information → return_in_transit → received_inspection → refund_pending → refunded / replacement_sent → completed / closed。

- 取消可单独为 cancelled_before_fulfillment、cancelled_after_payment 等原因，不覆盖付款状态。
- 支付服务商退款失败进入 refund_failed，保留案件并允许经授权重试或转人工处理。
- COD 未收款取消不生成退款；已收 COD 的退款通过商家确认的人工渠道记录。
- 一个订单可有多个售后案件，但同一订单/订单行的累计数量和退款不得超上限。

## 金额、支付和库存规则

1. 仅对已确认实收且未退金额创建支付渠道退款；部分退款累计不超过实际可退余额。
2. 在线支付服务端创建退款，保存幂等键、渠道退款号、请求结果和事件回调；未知状态先查询，不能直接重复退款。
3. 仅授权人员执行退款；超过配置阈值需二次审批。
4. 退款结果是交易记录，不直接改写原付款或订单金额快照。
5. 退回商品在收到并检查前不增加可售库存；质检后选择重新入库、损坏/冻结、报废或待决定。
6. 取消未发货订单按库存策略释放预留；已发货订单不自动恢复库存。
7. 退款后优惠券是否返还、折扣如何按行分摊由实例规则确认并显示在案件摘要。
8. 退款成功与案件完成是不同状态；若还需收货/补发，继续履约后才关闭案件。

## 数据对象

- AfterSalesCase：案件号、订单 ID、类型、状态、原因、创建来源、顾客说明、负责人、时间戳。
- AfterSalesItem：订单行 ID、申请数量、批准数量、商品处置状态、金额分摊快照。
- Refund：支付 ID、渠道、申请金额、币种、状态、外部退款 ID、幂等键、执行者、原因。
- ReturnShipment：退货物流方式、追踪号、寄出/收货时间、签收状态。
- InspectionRecord：收货数量、质检结果、库存处置、操作者和备注。
- CaseEvent/CaseNote：状态变更及内部/对客备注，敏感资料脱敏。

## 验收条件

- 可从订单建立案件并查看完整时间线，不改写已确认订单/支付快照。
- 未支付订单不能创建支付退款；COD 未收款取消不生成退款记录。
- 部分退款累计不能超过已收款可退余额；重复请求不会重复退款。
- 支付退款处理中/失败可观察、可对账并安全重试。
- 退货质检前商品不增加可售库存；不同处置结果产生库存流水。
- 退款审批、执行、顾客资料访问均按角色限制并记录审计。
- 顾客通知状态失败不丢案件或退款记录。
- 多语言原因、时间和金额展示一致；敏感资料遵循后台权限。

## 依赖与边界

依赖 M00、M07、M08、M09、M12。M13 通知作为案件状态事件的消费者；M10 会员/积分处理按已验证身份作为可选联动；M14 消费售后汇总。退款 API 能力取决于具体支付服务商；拒付争议、法务仲裁、自动退货面单、仓库系统、多仓换货和跨境税务重算不属于默认首期范围。
