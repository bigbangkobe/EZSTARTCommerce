# M08 付款方式与交易记录

**优先级：**P0  
**初步开发估算：**8–14 人日（原估算未完整计入结算文件对账；按确定的支付服务商、文件格式和 API 能力重新估算）

## 产品目标
以可替换方式管理货到付款和获批的线上支付服务。

## 首期范围
COD；后台维护已接入的付款渠道、启停状态和安全凭证引用；支付服务适配器；线上支付创建/回调/状态同步；交易记录；支付失败；退款能力由 M16 售后案件调用支付服务商适配器；是否支持 API 退款取决于选定服务商，人工退款也需记录渠道与凭据引用。
首期对账包括交易台账、服务商结算文件导入、自动匹配、差异队列、人工核实与审计。服务商 API 对账仅在所选服务商支持且单独完成集成后启用。

## 主要数据对象
PaymentMethodConfig（只存非敏感配置与密钥引用）；Payment（提供方、交易号、金额、币种、状态）；PaymentEvent；Refund；SettlementBatch；SettlementLine；ReconciliationMatch；WebhookLog（敏感数据脱敏）。密钥放密钥管理服务，不入数据库明文。结算银行账户由客户在支付服务商处绑定；本系统只显示服务商返回的脱敏账户摘要/连接状态，不保存网银凭据或完整银行账号。

## 关键业务规则
线上方式只有在业主和服务商批准后启用；后台提供凭证配置/密钥引用、测试环境与正式环境区分、连接状态、启停和操作记录。凭证保存后不再次明文展示。处理回调需验签、幂等和重放保护；订单支付状态以可信服务端事件或服务端查询更新。第三方开户、资质审核和交易费不在开发范围。

付款查询超时进入 `unknown`，默认在 1/5/15/30 分钟由服务端再查询；仍未知进入财务/客服待处理队列并继续接收回调。系统不得将未知改成失败，不得释放库存/优惠占位或重复发起付款。只有渠道明确返回失败/取消后，才能按 M06/M12 规则释放占位。

对账按支付、退款、服务商结算行和 COD 收款记录分别核对，不把“支付成功”误认为“已结算”。匹配至少校验服务商交易号、订单关联、币种和金额；差异分类为待结算、内部缺失、渠道缺失、金额不符、币种不符、重复行或需人工确认。系统不得因导入文件自动修改已确认付款/退款事实；人工处理差异须填写原因、保留原始行并记录操作者。文件重复导入须识别并阻止重复入账。

## 验收条件
COD 订单可正常建单并独立记录待收/已收/拒收/退回；线上支付可完成授权/成功/失败/处理中状态流转；重复或伪造回调不重复入账；后台可查看交易状态及错误原因。
支付配置可保存、脱敏查看、测试和启停；未获批准/未配置的方式不能在结账页展示。结算文件可预览后导入；重复文件不重复产生对账行；系统正确标记匹配和差异；差异解决有原因和审计记录；支付、退款及结算数据可按期间导出并追溯到订单/服务商交易号。

## 依赖
M06、M07、M01；服务商账户、沙箱和生产凭证。

## 项目实施建议
第 E/F 阶段；历史基础付款估算为 8–14 人日，须按服务商接口与结算对账方式重新估算，且受服务商影响最大。
