# 售后页面与交互设计

本文补充后台 M16 和顾客访客态售后入口。顾客端不因此获得账号、密码或持续登录会话。客户可以首期只启用客服人工登记；自助查询/申请须先配置安全的邮箱/短信验证。

## 1. 用户和目标

- 顾客：提交订单相关的取消、退货、换货或退款请求，并知道当前处理状态。
- 客服：核实订单和诉求，补资料、审核、分派、通知。
- 财务：核对实收金额，执行/确认退款，处理失败和对账。
- 仓库：登记退件、质检结果和库存处置。
- 店主：审批高额退款并查看售后趋势。

## 2. 前台页面 F11：访客订单查询（可选）

### 进入方式

订单确认通知中的短期安全链接，或订单查询表单。采用短期签名链接或向下单联系方式发送一次性验证码；订单号单独不足以验证身份。验证码有效期、尝试次数和限流可配置。

### 页面结构

查询入口 → 订单身份验证 → 订单摘要 → 状态与物流 → 需要帮助？联系商家/申请售后。

通过验证后只显示订单号、日期、商品与规格摘要、付款/履约状态、追踪信息和售后入口。地址和完整联系方式继续隐藏；不要暴露内部备注、支付凭证或风险标记。

### 状态

- 未验证：不显示订单是否存在；成功/失败提示一致，防止订单枚举。
- 验证中：限速并显示可重发时间，不提供无限次试错。
- 找不到或已过期：提供联系商家入口，不透露敏感订单信息。
- 已验证：显示最少必要字段和状态更新时间。
- 外部支付状态未知：显示“确认处理中”，不误显示已付款。

### 验收

- 不能仅靠可猜的订单编号读取订单。
- 验证码/短链不可重用、会过期并有尝试限制。
- 已登录后台权限与前台订单验证完全分离。
- 个人资料不写入网站分析事件。

## 3. 前台页面 F12：访客售后申请（可选）

### 表单

从已验证订单进入；选择订单商品和数量，选择请求类型（取消/退款咨询/退货/换货），填写原因和说明；仅在商家启用时要求上传图片。展示商家政策链接、提交后的案件编号及预计响应说明。

顾客不能提交自定退款金额；金额、可申请商品数量、可操作时间和资格由服务端检查。表单提交后只生成申请，不代表已批准或已退款。

### 提交后

显示“已收到申请”，给案件编号、联系渠道和状态查询方式；发送交易通知。后续补资料仍需验证身份或由客服联系。

### 边界

- 未发货取消、已发货退货和付款退款是不同请求类型。
- COD 未收款只记录取消/退货，不显示支付退款成功。
- 市场/商品政策文案由商家提供并按目标地区审查。
- 若没有已配置的验证渠道，前台隐藏自助入口，客服从后台建立案件。

## 4. 后台 M16 页面

### 售后列表

主操作“从订单创建案件”；支持按案件号、订单号、类型、状态、时间、支付方式和负责人筛选。列表突出需审批、退款失败、超时未处理和待收退件。顾客资料默认脱敏。

### 售后详情

页面分为订单/付款摘要、案件申请、商品与数量、处理动作、收货质检、退款记录、通知和审计时间线。顶部始终显示案件状态、负责人和允许的下一步。

重要动作按钮按照状态机出现；拒绝、退款、库存处置、关闭案件都需要选择原因并二次确认。退款弹窗显示实收额、已退额、可退余额、币种及渠道；服务端再做最终校验。

### 权限和审计

客服可建案与处理申请；财务可审批/执行退款；仓库可登记收货与质检；店主可管理额度和授权。禁止将“关闭案件”作为跳过退款或库存核对的快捷动作。每个操作写入操作者、时间、前后状态、金额/数量、理由和关联 ID。

## 5. 售后状态与通知

| 业务节点 | 顾客可见状态 | 内部状态/责任人 |
|---|---|---|
| 已提交 | 已收到申请 | 待审核/客服 |
| 补充资料 | 需要补充资料 | 等待顾客/客服 |
| 已批准 | 处理中 | 已批准/客服或仓库 |
| 退件途中 | 等待退件 | 退货运输中/仓库 |
| 已收件 | 质检处理中 | 已收件/仓库 |
| 退款处理中 | 退款处理中 | 退款待处理/财务 |
| 退款失败 | 商家正在处理退款 | 渠道失败/财务 |
| 已完成 | 已处理完成 | 已完成 |
| 未批准 | 申请未获批准，可联系商家 | 已拒绝/客服 |

顾客提示不暴露内部审核备注或风控标签。邮件/短信发送失败不回滚案件状态。

## 6. 验收与体验检查

- 用户知道提交的是“申请”，不误以为退款已经发生。
- 订单查询先验证再显示，过期/错误提示不泄露订单存在性。
- 金额、币种和数量与订单/付款记录一致；不同状态文案明确。
- 案件表单提供加载、校验失败、重复提交和服务失败状态。
- 无验证服务时自助入口关闭，后台人工创建仍可运行。
- 三种语言下错误、状态、金额和政策链接均能完整呈现。
