# EZSTARTCommerce 产品与技术总体蓝图

> 本文是产品与实施路线总览。技术栈、接口约定、数据/状态规则及生产门槛已冻结于 [开发执行规格](../03-开发文档/DEVELOPMENT_SPEC.md)；客户市场、第三方服务、云资源和实例配置仍按实例填写。前台定制方式的重做基线见 [配置化前台与交付体系重做方案](../06-产品设计逻辑/03-配置化前台与交付体系重做方案.md)。

## 1. 负责人结论

EZSTARTCommerce 应设计成一套**可复用的电商核心、商家管理后台和部署模板**。交付给每个客户时，独立部署一套后台与业务 API，前台由实例配置生成（品牌/配色/区块/文案/开关），换客户无需前端开发。独特流程按例外定制并单独报价。

核心判断如下：

1. **不是 SaaS。**本项目不建设共享租户数据库、商户自助开店控制台、跨店运营后台、平台订阅计费或跨商家数据分析。
2. **每家客户一个独立实例。**数据库、文件、管理员、第三方凭证、域名、备份和发布环境均隔离。可以由客户自托管，也可以代为托管独立实例；代托管不改变独立部署边界。
3. **后台和交易核心复用，前台由配置驱动。**商品、价格、库存、优惠、运费、支付校验和订单规则留在服务端；客户的品牌视觉、首页区块编排、文案和模块开关由实例配置决定，无需前端开发。
4. **第一阶段采用模块化单体。**一个清楚分域的后端服务和一套主数据库，后台任务由独立 worker 执行。避免为了“未来可能扩展”先拆微服务。
5. **烟草只是一个客户场景。**行业或地区特殊规则通过商品属性、店铺配置和明确的业务策略处理，不把烟草写死进通用电商核心。

## 2. 产品边界与设计原则

### 产品要解决的问题

让商家能通过后台自行维护商品、图片、分类、规格、内容、价格、库存、优惠券、付款和配送设置；顾客从该商家的配置化前台浏览并以访客身份下单；商家在独立后台履约、运营和看报表。

### 已确认的功能边界

- 访客购物和结账无需登录；会员可自愿使用无密码的一次性验证码登录。
- 前台语言为简体中文、繁体中文和英文；商品与内容可分别维护各语言版本。
- 商品、分类、品牌、规格、图片、价格、上下架、库存由后台管理，支持模板化批量导入。
- 后台管理订单、完整会员规则、会员中心、优惠券、库存预警、内容、通知、经营报表与站点访问分析。
- 支持货到付款；信用卡或其他线上方式通过支付服务商配置和适配器接入。
- 每家商户都有自己的专属前台，由实例配置生成；通用前台即配置驱动的可复用基线。
- 用户提供的网站仅作业务、页面和展示参考；没有旧站后台、源代码或数据库，不据此承诺后台复刻或数据迁移。

### 设计原则

- **配置优先、定制例外：**品牌、配色、字体、首页区块、文案、政策、优惠规则等由实例配置改，无需前端开发；仅当客户需要全新页面行为或独特交互时走 B/C 类例外定制并单独报价。
- **不承诺万能拖拽搭建器：**首期提供声明式区块注册表驱动的首页模块与内容区配置；需要注册表之外的新页面行为时走定制开发。
- **交易由服务端裁定：**浏览器传来的价格、折扣、库存、运费均不可信，提交订单时重新校验。
- **业务数据先准确，再做报表：**订单与支付台账是销售金额的权威来源，访问统计不能反向决定财务数据。
- **升级不覆盖客户差异：**核心后台、API 和配置化的前台主题分别版本化；实例配置与代码分离，升级不覆盖客户配置，客户前台通过稳定 API 连接对应独立实例。

## 3. 用户与主要旅程

### 商家负责人

开通独立实例 → 初始化品牌、语言、市场、付款和配送 → 邀请后台员工并分配权限 → 维护商品和内容 → 发布前台 → 监控订单、库存、优惠和经营数据。

### 商品运营人员

导入或新增商品 → 维护三语内容、图片、规格、价格和库存 → 预览前台 → 发布或下架 → 查看导入错误和库存预警。

### 订单与客服人员

查看新订单 → 联系顾客或确认货到付款 → 更新处理状态 → 安排配送 → 记录取消、退款或异常 → 触发顾客通知。

### 顾客

访问专属前台 → 搜索/浏览 → 查看商品规格和库存 → 加入购物车 → 使用优惠券 → 填写必要联系与配送信息 → 选择已启用付款方式 → 提交访客订单 → 收到订单确认。

订单查询入口、税务规则、退款资格与市场销售限制仍需在目标市场范围冻结后确定；售后案件页面与状态基线见 design/AFTERSALES.md。

## 4. 产品信息架构

### 客户前台

前台由每个客户的页面清单决定，通常考虑：

- 首页：品牌主视觉、精选分类、活动区、推荐商品、信任与配送说明。
- 分类/搜索：筛选与排序、价格、库存、规格选项、空结果和分页。
- 商品详情：多语言标题与说明、图片、变体、价格、库存提示、配送/退换政策。
- 购物车：商品和规格、数量修改、优惠码、预估运费、应付金额。
- 结账：联系信息、配送地址/区域、配送方式、付款方式、订单复核。
- 订单结果：成功/待付款/付款失败等状态、订单编号和后续指引。
- 内容页：品牌介绍、FAQ、联系资料、配送政策、隐私/条款等。
- 语言切换、SEO 元数据、移动端导航和客服入口。

不是每位客户都必须有完全相同的这些页面；页面结构、专题页和特殊交互由每份客户范围清单约定。

### 商家管理后台

建议后台导航按经营任务组织：

1. **总览：**销售额、订单数、待处理订单、低库存、优惠活动和近期异常。
2. **商品：**商品、分类、品牌、规格、图片、三语文案、上下架和批量导入。
3. **订单：**订单列表、订单详情、状态流转、付款/配送记录、顾客通知。
4. **售后：**售后案件、取消/退款、退货/换货、收货质检、金额审批与时间线。
5. **顾客/会员：**后台 CRM、等级/积分/权益、订单关联和营销同意；会员中心采用 OTP 会话，不设密码，访客结账不受影响。
6. **促销：**优惠券创建、批次/发放、适用商品或分类、有效期、额度和核销记录。
7. **库存：**SKU 现货、预留、可售量、变更流水、低库存阈值和预警。
8. **内容：**页面、FAQ、公告、文章、导航、首页可配置内容区及语言版本。
9. **配送与付款：**区域、计费规则、货到付款、获批线上支付方式及凭证状态。
10. **数据统计：**经营报表、商品/库存表现、匿名访问来源、商品浏览、加购、结账和下单漏斗。
11. **店铺设置：**品牌、域名、语言、币种、时区、市场、客服资料和通知模板。
12. **用户与安全：**后台用户、角色、权限、审计日志、会话和安全设置。

一个商家实例内可以有多名员工及不同角色；这不是多个商家共用一套后台。

## 5. 前端产品与代码设计

### 前台定制分层

| 层次 | 后台配置内容 | 前端开发内容 |
|---|---|---|
| 基础资料 | 品牌名、标志、客服、导航文字、政策、语言内容 | 页面如何呈现、响应式适配 |
| 商品运营 | 标题、描述、图片、价格、规格、库存 | 商品卡片/详情布局、筛选和规格选择交互 |
| 活动运营 | 优惠券规则、活动标题/图片/时间 | 专题页、活动视觉和独特交互 |
| 交易设置 | 付款、配送、市场可用性 | 结账页面的呈现与步骤体验 |
| 客户专属 | CMS 可配置的通用内容块 | 不同信息架构、特殊组件、独有流程和品牌设计 |

凡会影响应付金额、优惠资格、库存扣减、支付状态或下单资格的决定必须由后端执行。

### 工程边界

- 建立一套通用的前台组件和参考实现，帮助启动新客户项目，不强迫客户共用整套页面。
- 每个客户前台以独立应用包/项目构建和发布；共用的是经过抽象的商品卡片、价格格式化、购物车状态等基础能力，而非把客户页面硬塞进配置开关。
- 前台不直连数据库；所有业务读取与写入通过版本化 Storefront API。
- SEO、首屏速度、图片尺寸、键盘操作、移动端触控和错误状态属于页面验收的一部分。
- 后台管理的页面内容要使用有类型约束的数据结构，不能让客户输入任意脚本或 HTML 后在其他页面直接执行。
- 客户定制源码的仓库、源码归属、客户是否可修改及交付形式须写入商业约定。

### 两种仓库策略

推荐产品团队先使用一个工作区管理公共核心、后台、API 和示例前台；客户项目放独立前台包，版本依赖公共 API 契约。若客户需要独立拥有全部源码或限制访问，再在交付时拆分源码仓库/镜像仓库。无论仓库如何组织，禁止客户专属业务规则无审查地分叉进公共核心。

## 6. 后台、API 与后端领域设计

### 后端模块边界

模块化单体中的模块应有清楚的输入、输出和数据所有权：

- **Identity/Admin：**后台认证、用户、角色权限、操作日志。
- **Store Config：**语言、时区、币种、品牌、市场和功能开关。
- **Catalog：**商品、翻译、分类、品牌、SKU/变体、媒体关联。
- **Content：**页面、FAQ、导航、文章及翻译。
- **Cart/Checkout：**访客购物会话、价格校验、优惠、配送报价和下单。
- **Orders：**订单快照、状态机、取消与人工处理。
- **Payments：**货到付款与线上支付适配器、回调验签、退款记录。
- **Fulfillment：**配送区域、计费、发货及物流信息。
- **Customers/Promotions/Inventory：**顾客资料、优惠券核销、库存流水与预留。
- **Notifications：**交易通知模板、发送任务、重试和失败记录。
- **Analytics/Reporting：**匿名访问事件、聚合指标、经营报表和导出。
- **Import/Export：**文件暂存、字段映射、验证、执行和逐行错误报告。
- **AfterSales：**售后案件状态、退款协调、退货质检和库存处置。

模块之间通过应用服务/领域接口交互，不允许后台控制器直接绕开库存、优惠或订单规则修改其他模块的数据。

### API 分层

至少分出两个逻辑接口面：

- **Storefront API：**公开可访问的商品、分类、内容、购物车、配送报价、优惠验证和访客下单入口。
- **Admin API：**要求认证和权限，提供商品、订单、内容、运营、统计和配置管理。

两者可以由同一个后端部署，但路由、鉴权、速率限制和审计要求不同。建议接口带版本号，如 /api/v1；用 OpenAPI 固定请求/响应结构并生成前端客户端。付款回调使用独立端点并验证签名。文件上传经授权生成短时上传目标，限制格式和大小。

关键接口需要幂等语义：创建订单防重复提交、支付 webhook 防重复入账、库存调整保留请求 ID。公开接口对高频搜索和下单增加速率限制。

### 核心交易链路

1. 前台创建短期访客购物会话；浏览器的购物车金额仅用于展示。
2. 结账时后端重新查商品/SKU、当前价格、库存、优惠资格、配送区域和应付金额。
3. 后端以数据库事务锁定或原子更新涉及的库存，创建订单项目快照、状态历史和库存预留。
4. 货到付款订单进入待处理/待确认状态；线上付款订单进入待付款并在服务端向支付方创建交易。
5. 支付方回调先验签，再用唯一事件 ID 幂等更新支付状态和订单状态。
6. 订单状态变化通过后台任务发送邮件或其他已配置通知；失败重试，达到上限后进入人工处理。
7. 取消、超时或支付失败按明确规则释放库存预留；实际扣减时点须在订单流程确认阶段冻结。

### 模块化单体的演进条件

当不同模块已经遇到独立扩容、独立发布或故障隔离的实际瓶颈，再按边界拆服务。优先拆耗时或吞吐明显不同的 worker/分析流水线；支付、库存、订单等强一致交易域不因技术时髦而提前分布式化。

## 7. 数据模型与数据治理

### 核心实体

- 商店实例配置、语言/市场配置、管理员/角色/权限/审计。
- Product、ProductTranslation、Variant/SKU、Category、Brand、MediaAsset。
- ContentPage、NavigationItem、Translation。
- Cart、CartItem、CheckoutSession。
- Order、OrderItem 快照、OrderAddress、OrderStatusHistory。
- Payment、PaymentEvent、Shipment、Coupon、CouponRedemption。
- Customer、MemberProfile、MembershipTier、PointAccount、PointLedger、OtpChallenge、CustomerTag、ConsentRecord。
- InventoryItem、StockMovement、OrderReservation。
- NotificationJob、ImportJob/ImportRowResult、AnalyticsEvent、DailyMetricRollup。

### 必须坚持的数据规则

- 订单保存购买时的商品名称、规格、SKU、价格、优惠、运费、税额（适用时）、语言和币种快照。
- 金额用整数最小货币单位，不能用浮点数相加；每笔记录保存币种代码。
- 交易时间以 UTC 保存，管理后台按实例配置的时区展示。
- 每个客户独立数据库是主要隔离边界；不要为了没有确认的 SaaS 需求把行级 tenant_id 当安全隔离机制。
- 每个独立实例可以存一个部署/商店标识用于迁移、日志和导出，但它不代表共享租户运行模式。
- 顾客联系方式和地址按最小必要原则收集；日志和事件分析不得写入完整个人资料、密码或支付敏感数据。
- 导入先进入暂存区，预览字段映射与错误后再提交；支持部分成功报告和可审计的重试。

### 分析与报表的分界

- **经营报表**从订单、支付、退款、库存等业务账本聚合；财务口径必须明确退款、税额、运费和时区。
- **网站分析**从匿名事件形成来源和漏斗：page_view、view_item、add_to_cart、begin_checkout、purchase 等；事件不存姓名、邮箱、电话或地址。
- MVP 可先将事件和日汇总存于实例自己的主数据库；数据量增加后才为分析存储单独评估列式数据库/事件仓库。
- 商家只查看自己的事件和报表；默认不集中传到模板提供方。事件同意、保留期和归因规则按目标市场及商家策略确认。

## 8. 技术架构与选型

### 已冻结技术基线

| 层次 | 建议 | 选择理由/边界 |
|---|---|---|
| 客户前台 | TypeScript + Next.js 16，客户各自的前台应用 | 服务端渲染/搜索页；独立构建发布，调用该客户 API |
| 商家后台 | TypeScript + Next.js 16 + React 独立管理应用 | 与顾客页面在路由、会话和权限上隔离 |
| 后端 API/Worker | Node.js 24 LTS + NestJS 12 模块化单体，REST/OpenAPI | Worker 复用领域代码并独立进程运行 |
| 主数据库 | PostgreSQL 18；ORM 为 Prisma 7 GA，交易锁与原子操作明确使用事务/参数化 SQL | Prisma 8 GA 和兼容评审完成前不进入首期；交易使用关系约束、事务和行锁；每客户独立数据库 |
| 异步任务 | PostgreSQL outbox/job 表 + Worker | 首期不依赖 Redis；任务可重试、幂等并进入死信状态 |
| 图片/导入文件 | S3 兼容对象存储 | 媒体与数据库分离；每个客户独立空间和备份 |
| 包管理/部署 | pnpm workspace；Docker 镜像 + Docker Compose | lockfile 锁定依赖；每客户独立部署配置 |
| 监控 | 结构化日志、错误追踪、健康检查、可观测指标 | 日志脱敏；每实例有独立备份/恢复责任人 |

技术基线已冻结；精确依赖 patch 由 lockfile 固定，更新走评审和迁移流程。详见 [开发执行规格](../03-开发文档/DEVELOPMENT_SPEC.md)。

### 逻辑部署图

~~~mermaid

  A[商家员工浏览器] --> RP

  API --> Q[后台任务队列]
~~~

每位客户各有自己的这套部署边界。内部工程团队可以维护共同代码和发布制品，但不因此拥有共同商家数据的运营总控台。

### 部署形态

- 小型客户：一台云主机或容器主机运行反向代理、前台、后台、API、worker 和独立数据库；按容量决定数据库是否使用托管服务。
- 正式交易环境：数据库与媒体备份独立于应用主机；授权管理员可从后台安全录入支付密钥，后端写入密钥存储并仅在数据库保存引用；初始密钥也可由受限部署配置注入。密钥不提交源码、不回显、不放普通日志。结算银行账户在服务商商户后台绑定，本系统仅查看脱敏连接状态。
- 不以单机容器本身作为备份；备份应在独立存储中加密，并进行恢复演练。
- 每次发布固定应用版本和迁移版本：备份 → 测试升级 → 执行迁移 → 健康检查 → 观察 → 必要时回滚。
- 每个客户的配置、数据库连接、密钥、域名和发布凭证都独立；运维支持访问要授权、限时并留审计。
- 不因为客户数量增加就默认为一套集群里的共享多租户 SaaS。

## 9. 安全、隐私与质量基线

- 后台使用安全会话；关键角色启用多因素验证，登录限速，密码和会话采取成熟安全机制。
- 采用 RBAC 最小权限；导出顾客、退款、调价、库存更改、权限变更都写审计日志。
- 防护 CSRF、XSS、SQL 注入、请求伪造、上传恶意文件、CSV 公式注入、订单重复提交和 webhook 重放。
- 支付系统不保存卡号、CVV 等卡片敏感数据；尽量使用支付服务商托管支付页或令牌化组件。
- API 对金额、地址、库存和折扣作服务端验证；管理员上传图片进行 MIME/大小限制和安全扫描策略。
- 日志脱敏；环境密钥分离；依赖更新和漏洞处理要有维护流程。
- 个人资料仅用于订单履约和经明确批准的运营目的；营销通讯与交易通知分开记录。
- 个人资料请求走独立权限与审计工作流：先核验身份，再按授权范围生成限时导出；删除/匿名化与订单、付款和售后事实分离，处理时限和保留例外由客户配置。
- 发布的 SEO 元数据必须由搜索引擎可读取的渲染输出提供；路由层按语言生成 canonical/alternate、Sitemap 和 robots，并在 slug 变更时校验 301 重定向冲突与循环。
- 市场、商品、支付、宣传内容和可能要求的年龄/地区限制，由商家及其专业顾问确认后配置；系统不得默认某个行业或市场已获准经营。

### 建议的初步非功能指标

以下是可在需求工作坊确认的规划目标，不是已经承诺的 SLA：

- 典型商品列表、详情和后台列表在正常网络及目标数据量下满足商定的响应时间预算。
- 关键读接口和写接口具有稳定的分页上限、超时、限流和错误日志。
- 生产数据库有自动备份、恢复演练、健康检查和告警责任人。
- 至少有测试/预发布和生产配置；上线前完成支付回调、数据恢复和权限验收。
- 以目标主机规格和预计商品/订单量完成容量估算后，才冻结并写入合同的 uptime、RPO、RTO 和支持响应时间。

## 10. 迭代与交付顺序

### 第 0 阶段：需求与风险冻结

冻结首发市场、商品/市场审核责任、货币/税务、付款服务商、运费规则、取消/退款、库存扣减时点、分析数据留存和客户源码权利。交付端到端流程、范围清单、原型、数据字典与验收用例。

### 第 1 阶段：可重复部署与管理框架

实现独立实例初始化、后台登录与权限、操作审计、店铺配置、媒体上传、版本迁移和备份恢复；空环境可重复装出一套客户实例。

### 第 2 阶段：商品和内容运营

完成商品/规格/分类/多语言、图片、页面内容、批量导入预览与错误报告；后台编辑后能在配置化前台正确显示。并完成前台配置引擎骨架（ThemeConfig 发布快照 + 前台读取 + CSS 变量注入），使品牌、配色、首页区块可配置。

### 第 3 阶段：购物到订单

完成访客购物车、优惠校验、运费报价、结账、订单快照、库存预留和货到付款；线上支付仅在服务商及业务审核完成后接入。基础售后/退款案件与订单闭环同步实现，复杂退换货物流另行评估。

### 第 4 阶段：运营、统计和消息

完成订单处理、通知、顾客后台资料、优惠券、库存告警、经营报表、匿名行为漏斗与导出。

### 第 5 阶段：第一个客户前台和上线

以烟草客户为第一个独立前台项目，按批准的页面清单和设计稿单独估算、开发和验收；连接独立后台 API，做移动端、语言、交易金额和异常流程验证，再私有部署上线。

### 第 6 阶段：复制交付

用另一份空白独立实例演练安装、配置、导入、升级、备份、恢复和密钥替换；将这条开通链路整理成重复执行的客户交付手册。

每阶段结束以可演示成果和验收标准判定，不以完成了多少代码行作为进度指标。

## 11. 成功指标与产品质量

### 商家效率

- 新实例从部署到管理员能登录的时长。
- 商品新增/批量导入成功率、失败行可诊断性和平均上架耗时。
- 运营人员处理一个新订单的步骤和平均用时。
- 库存告警的准确率及误报情况。

### 顾客交易体验

- 商品详情到加购、结账开始到下单的漏斗转化。
- 结账失败率、支付回调失败率、重复订单率。
- 移动端关键页面加载时间与表单完成率。
- 三种语言的页面和交易字段完整率。

### 软件交付质量

- 新客户实例部署成功率及人工步骤数量。
- 核心/API 升级后客户前台兼容率。
- 备份恢复演练成功率和恢复耗时。
- 生产缺陷、权限事故和数据错账次数。

指标必须注明分母、时区、退款口径和事件同意策略，避免漂亮但不可解释的数字。

## 12. 逐店确认的上线参数

共用产品和技术规则已经冻结于 [开发执行规格](../03-开发文档/DEVELOPMENT_SPEC.md)。每家店只需补充会因经营主体、地区、服务商或合同变化的实例参数：

1. 首发国家/地区、允许商品、营销/年龄限制及负责签署审查的人员。
2. 单店基础币种、税费/含税口径和是否需要发票；默认单币种、税费关闭。
3. 线上支付服务商/审批、商户凭证、退款能力、结算文件/API 和服务商绑定结算账户的完成状态。
4. COD 区域/金额上限/确认人；客户若要更改线上预留时限或状态流转，作为书面变更评估。
5. 配送区域、固定费率/免运门槛、预计时效和拒收/退回处理；自动物流为单独范围。
6. 会员等级/积分/权益和售后资格/审批/返券参数；复杂叠券需要范围变更。
7. 邮件/短信/WhatsApp 账号、已批准模板、顾客订单查询是否纳入首期。
8. 数据同意/隐私政策、个人资料留存期、请求联系人/时限、分析告知和事件保留规则。
9. 客户前台页面/状态/交互清单、桌面/移动设计稿、三语内容负责人、源码/IP、自改和升级责任。
10. 云账号/区域、域名、备份目标、RPO/RTO、告警联系人、支持时段及安全升级责任。

## 13. 范围与估算边界

历史规划基线 181–277 人日（原核心加 M16 售后）不再覆盖当前完整范围，不得作为最新报价。新版还明确纳入会员扩展、结算文件对账、分批发货/库存超时恢复、强制 MFA 与会话管理、前台配置引擎及陈列配置、生产就绪验收；需按模块更新估算后再定工期和预算。B/C 类例外定制、支付/物流差异集成和内容生产仍需单独估算。

标准客户按配置级交付报价：底座授权 + 标准部署 + A 类配置 + 维护升级（见 [商业分层与报价模型](COMMERCIAL_MODEL.md)）。仅 B/C 类客户单独报价：业务发现与页面盘点、UX/UI、前端开发、Storefront API 差异联调、内容迁入、支付/配送差异、独立部署和后续维护。
